# 0008. База проверяется встроенным PostgreSQL-совместимым runtime, граница проверки называется явно

Дата: 09.09.2026

## Контекст

Спецификация требовала поднимать PostgreSQL 16 и Redis через Docker Compose. На машине
сборки Docker в PATH не обнаружен, а миграции всей схемы и безопасную выборку каталога
надо было чем-то проверить, не откладывая приёмку.

## Решение

Схема и выборки проверяются встроенным PostgreSQL-совместимым runtime, который
поднимается внутри самого теста — без демона, контейнера и внешнего сервиса. Compose
остаётся единственным способом получить настоящие PostgreSQL 16 и Redis; тесты против
них готовятся отдельно и выполняются в CI.

Граница проверки называется явно и всегда: пройденные тесты не выдаются за проверку на
PostgreSQL 16, а список непроведённых проверок — PostgreSQL 16, Redis и BullMQ, реальные
ответы МойСклад, запись в S3 — перечисляется в README и в записи таска. «Тесты зелёные»
без указания, на чём именно, в этом проекте не считается отчётом.

## Почему

Рассматривали и отвергли:

- **Считать тесты пройденными, раз среда недоступна.** Отвергнуто прямо и первым:
  непроверенная миграция — самый дорогой вид «готово», потому что обнаруживается на
  первом развёртывании, когда база уже не пустая.
- **Мокать базу и проверять SQL сравнением строк.** Дёшево и работает везде. Отвергнуто
  потому, что проверяет единственное: что запрос не изменили. Вопрос же стоит иначе —
  исполним ли он и создаёт ли миграция то, что обещает.
- **Остановить работу до установки Docker.** Отвергнуто: установка демона на машину
  пользователя — не то решение, которое принимает исполнитель таска, а фундамент
  Этапа 1 ждать этого не может.
- **Перенести все проверки БД в CI и локально не проверять.** Отвергнуто: обратная связь
  удлиняется до push, и локальный цикл разработки остаётся вовсе без тестов базы — то
  есть менять схему становится страшно.

## Последствия

- Два набора проверок и два runtime вместо одного: их придётся держать в согласии, и
  расхождение между ними — отдельный источник работы.
- Совместимость не равна тождеству. Расширения, роли и права, поведение конкурентных
  транзакций, специфика планировщика остаются вне зоны локальной проверки; расхождение
  возможно и всплывёт в CI, а не на разработческой машине.
- Отчёт исполнителя обязан называть границу проверки — дисциплина, которой раньше не
  было и которую легко потерять при спешке; потерянная, она возвращает нас к первому
  отвергнутому варианту, только незаметно.
- Часть Этапа 1 остаётся честно непроверенной до появления среды. Этап не объявляется
  закрытым по факту зелёных локальных тестов.

## Уточнение 09.09.2026: предпосылка «Docker недоступен» была неверной

~~На машине сборки Docker в PATH не обнаружен~~ — эта строка «Контекста» не подтвердилась.
Docker в системе есть, и был всё это время. Проверено запуском 09.09.2026: `docker --version`
отвечает, Compose отвечает тоже.

Падал не Docker, а `pnpm infra:up`: порт 5432 занят посторонним контейнером PostgreSQL,
не имеющим к «Вистерии» отношения. Compose «Вистерии» публикует postgres ровно на 5432
и получает отказ вида «port is already allocated», после чего redis из того же прогона
поднимается нормально. **Занятый порт — не то же самое, что отсутствие демона**, и разница
между двумя этими диагнозами стоила прогону всей ветки рассуждений выше.

Независимая приёмка подняла PostgreSQL 16 отдельным контейнером на свободном порту.
Повторная проверка 09.09.2026 подтвердила: миграции применяются на настоящем PostgreSQL 16,
повторный прогон идемпотентен, набор `@visteria/db` — 7 тестов из 7 зелёные не на встроенном
runtime, а на живой базе.

**Точность о том, что именно прогнано на PostgreSQL 16.** Переменная `TEST_DATABASE_URL`
переключает тесты одного пакета — `@visteria/db`. Наборы `apps/api` и `apps/sync-worker`
создают встроенный runtime безусловно, эту переменную не читают и на живую базу от неё
не переезжают. Формулировка «весь набор прогнан на PostgreSQL 16» была бы тем самым
отчётом «тесты зелёные» без указания, на чём именно, — который эта запись и запрещает.

Решение не отменяется: встроенный runtime остаётся умолчанием локального цикла, а граница
проверки по-прежнему называется явно. Меняется основание — не «Docker недоступен», а «живая
база не должна быть условием того, чтобы прогнать тесты». Отвергнутый вариант «остановить
работу до установки Docker» отпадает вместе с предпосылкой: устанавливать нечего.

Актуальный порядок локального запуска, ловушка занятого порта и команда запуска PostgreSQL 16
на свободном порту — `docs/local-development.md` в репозитории кода `visteria-website`.
