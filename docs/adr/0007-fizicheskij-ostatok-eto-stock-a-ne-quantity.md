# 0007. Физический остаток берётся из stock; контракт остатков проверен по документации API

Дата: 09.09.2026

## Контекст

ТЗ интеграции (`05_website-plan/02_moysklad-integration.md` §5.1) называло физическим
остатком показатель `quantity` краткого отчёта. Перед первым таском синхронизации
официальный контракт JSON API 1.2 был сверен по публичным файлам документации
(05.09.2026, без ключей и обращений к аккаунту) и опроверг эту трактовку.

## Решение

Физический остаток переносится из показателя `stock`, доступный — из `freeStock`.
Показатель `quantity` не используется как физический остаток нигде: он учитывает и
резерв, и ожидаемую поставку. Один запрос отдаёт один показатель, и поле в ответе
носит имя показателя.

Отсюда ещё три обязательства, продиктованные тем же контрактом:

- Краткий отчёт `report/stock/bystore/current` — массив верхнего уровня без `rows`,
  `meta` и пагинации; он читается целиком, постранично не обходится.
- Глубина `changedSince` ограничена сутками. Курсор старше — не повод отправить
  недопустимый параметр, а повод перевести прогон в полную сверку. Интервалы
  перекрываются нахлёстом, курсор сохраняется только после успешной записи всех
  запрошенных показателей.
- `storeId = null` означает резерв без назначенного склада и произвольному складу не
  приписывается; `null` ещё не пересчитанного показателя не записывается нулём —
  прежнее значение живёт до следующего успешного обновления.

## Почему

Это случай, когда проверка источника опровергла план, а не уточнила его. Ошибка была
тихой: `quantity` — правдоподобное число, оно совпадает с физическим остатком ровно до
первого резерва и первой поставки в пути, то есть расходится редко и невоспроизводимо.

Рассматривали и отвергли:

- **Довериться ТЗ: оно ближе к предметной области, чем читатель документации.**
  Отвергнуто потому, что цена ошибки — витрина, показывающая наличие того, чего на
  складе нет, и прячущая то, что есть; разбираться с этим пришлось бы по жалобам
  покупателей, а не по журналу.
- **Переносить `quantity` и вычитать резерв самостоятельно.** Отвергнуто: резерв в
  `quantity` уже вычтен, второе вычитание уводит остаток в минус, а товар в пути
  остаётся прибавленным.
- **Обходить краткий отчёт постранично, как остальные эндпойнты.** Единообразно и
  потому соблазнительно. Отвергнуто: пагинации там нет, и цикл либо не завершится,
  либо молча возьмёт первый ответ за весь отчёт.
- **Отправлять `changedSince` старше суток и разбирать отказ.** Отвергнуто: отказ
  неотличим от временной ошибки, попадёт в повторы, и синхронизация встанет ровно
  там, где обязана была сверить каталог полностью.
- **Считать `null` пересчитываемого показателя нулём.** Отвергнуто: на время пересчёта
  товар исчезает с витрины и возвращается сам — самый труднообъяснимый вид дефекта.

## Последствия

- Расхождение разрешено в пользу контракта API: §5.1 правится, а не обходится кодом.
  Оставить ошибку в ТЗ означало бы, что следующий читатель повторит её заново — а
  ради этого запись и написана.
- Показателей три, запрос отдаёт один — прогон стоит трёх обращений вместо одного, и
  лимиты API расходуются соответственно.
- Полная сверка перестаёт быть аварийным режимом: любой простой воркера дольше суток
  штатно переводит следующий прогон в полный. Эта ветка должна оставаться рабочей и
  укладываться в лимиты, а не быть «на всякий случай».
- Сверка сделана по документации, а не на живом аккаунте. До первого прогона с
  действующим `MOYSKLAD_API_TOKEN` контракт считается проверенным на уровне
  документации, и так это и записано — детали могут отличаться.
