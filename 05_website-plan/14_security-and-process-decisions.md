# Решения по безопасности и процессу разработки — сессия /grill-me

Дата: 02.09.2026. Статус: зафиксированные решения после структурированного интервью перед стартом Этапа 1 (`07_roadmap-phases.md`). Дополняет, не заменяет `08_nonfunctional-security-ops.md`, `09_workflow-tooling.md`, `10_pre-development-checklist.md`, `13_server-capacity-and-services-plan.md`.

## 1. Область запуска

- **МойСклад**: платный тариф подтверждён (поддерживает вебхуки).
- **Порядок**: розница первой (Этап 2), опт — отдельным Этапом 5, как и было заложено по умолчанию.

## 2. Вход и роли

- Клиенты (розница/опт) — Telegram Login Widget + VK ID/OAuth, как и было спроектировано в `05_personal-cabinet.md`.
- **Manager/admin — тот же Telegram/VK-вход, плюс обязательный TOTP** (рекомендован Яндекс Ключ) при входе в управленку. TOTP выбран вместо кода через тот же Telegram/VK-канал, потому что код в том же канале — не независимый второй фактор (компрометация Telegram-аккаунта ломает оба «фактора» разом).
- Роль `manager`/`admin` никогда не присваивается через обычный флоу — только через allowlist конкретных `telegram_id`/`vk_id`, заданный вручную в БД/конфиге.
- Сетевой доступ к `admin.<домен>` — дополнительно ограничить (IP-allowlist/VPN), не полагаться только на проверку роли в приложении.

## 3. Процесс разработки с AI-агентами

- Схема «роут»: **Opus 5 — «босс»** (планирует и ревьюит, не пишет код сам), **GPT-5.6 Sol — воркер** (строит/чинит), цикл идёт, пока «босс» не одобрит.
- **Граница с продом**: цикл «босс/воркер» работает только с репозиторием и локальным/staging окружением на тестовых (sandbox) ключах МойСклад/Сбербанка. Прод-деплой — отдельный, осознанный шаг вне цикла, вручную инициируется заказчиком; на проде ИИ может помогать выполнять команды, но напрямую с ключами не работает (по аналогии с дисциплиной из `AGENT_SERVER_SETUP_TASK.md`: секреты создаются/читаются на сервере, но не печатаются в чат).
- Ревью кода целиком — на «боссе», у заказчика нет ресурса на security-код-ревью; заказчик выступает как тестировщик (проверяет работоспособность руками). Поэтому «боссу» нужен явный security-чек-лист (раздел 5 ниже), а не общая инструкция «пиши безопасно».
- Локальная разработка — Docker-образ поднимается на компьютере разработчика; минимальный staging на боевом сервере обязателен для тестов реальной оплаты (Сбербанк sandbox) — заложить `mem_limit`/CPU-лимиты на staging-контейнеры в Compose, чтобы нагрузочный тест на staging не мог просесть прод на одном физическом сервере.

## 5. Security-чек-лист для ревью «босса» (Opus)

Обязателен для кода в этих четырёх зонах — попадает в системный промпт/инструкцию «босса» как жёсткое условие approve, не общая рекомендация:

**а) Платежи (Сбербанк Эквайринг)**
- Сумма конвертируется в копейки только на границе интеграции с API Сбербанка; нигде в собственной БД/бизнес-логике не хранится и не сравнивается как копейки или как float (только `numeric(12,2)` в рублях).
- `sberbank_order_id` не путается и не смешивается с `moysklad_order_id` — отдельное поле, отдельная логика.
- Callback/notification-обработчик — тонкий: кладёт событие в очередь и отвечает быстро, тяжёлую бизнес-логику не выполняет синхронно.
- Есть fallback-проверка «зависших» неоплаченных заказов — оплата не подтверждается только по факту возврата на `returnUrl`.
- Сумма к оплате нигде не принимается от клиента напрямую без пересчёта/проверки на сервере.
- `refund.do` не может быть вызван без проверки прав вызывающего и принадлежности заказа.

**б) Проверка подписи/токена входа (Telegram Login Widget / VK ID)**
- Хэш Telegram Login Widget проверяется на backend через bot token (HMAC) при каждом входе — не только один раз «на глаз».
- VK OAuth-токен валидируется через VK API на backend, а не принимается как есть от клиента.
- `telegram_id`/`vk_id`, пришедшие от клиента без подтверждённой подписи/токена, никогда не доверяются.
- Сессия/JWT выпускается только сервером после успешной проверки, не конструируется на клиенте.

**в) Назначение/изменение роли пользователя**
- Ни один публичный API-эндпоинт не принимает `role` как поле, присваиваемое напрямую по запросу клиента.
- Присвоение `manager`/`admin` возможно только через allowlist `telegram_id`/`vk_id`, заданный вручную (не через код приложения на лету).
- Вход с ролью `manager`/`admin` требует TOTP-проверки на backend при каждой попытке — не только при регистрации второго фактора.
- Доступ к `admin.<домен>` дополнительно проверяется на сетевом уровне (IP-allowlist/VPN), отдельно от проверки роли в приложении.

**г) Обработчики вебхуков (МойСклад, Сбербанк)**
- URL содержит непубличный секретный сегмент пути.
- `accountId`/структура payload валидируются перед обработкой события.
- `requestId` используется для дедупликации повторных доставок.
- Обработчик отвечает 200/204 быстро (укладывается в лимит МойСклад 1500 мс), тяжёлая логика — асинхронно через очередь.
- Эндпоинт принимает только POST и имеет собственный rate-limit, отдельный от общего API.

## 6. Инфраструктура

- **Сервер**: апгрейд выполнен до 2 vCPU / 4 ГБ RAM (было 1/1) — сделан до старта Этапа 1, как и рекомендовал `13_server-capacity-and-services-plan.md` §8. Базовый чек-лист `AGENT_SERVER_SETUP_TASK.md` закрыт 17/17.
- **Домен**: вистерия74.рф, punycode-форма `xn--74-dlcmob9cgj7k.xn--p1ai` — использовать punycode при настройке callback/webhook URL в личных кабинетах МойСклад и Сбербанка, если кириллица не принимается напрямую. TLS — автоматически через Caddy/Let's Encrypt.
- **Бэкапы**: Яндекс S3 (тот же провайдер, что и для изображений товаров, отдельный бакет/префикс с шифрованием) как единственное основное место — от бэкапа на личный ноутбук отказались (риск: устройство не всегда онлайн, единая точка отказа, PDн в открытом виде на потребительском устройстве). Хранение: 7 ежедневных + 4 недельных (lifecycle-правило на бакете вместо ручной чистки).
- **Мониторинг/алерты**: получают заказчик и менеджер/администратор.
- **Email**: самостоятельный Postfix на сервере, почта `info@вистерия74.рф` уже создана на Beget. Решение — делать это правильно, но не блокировать запуск: обязательно настроить SPF/DKIM/DMARC на домене и проверить/запросить у Beget корректную обратную DNS-запись (PTR) и репутацию IP (blacklist-чекеры) до того, как транзакционные письма станут единственным способом связи с клиентом. Email считается вторичным каналом — Telegram (уже спроектирован как основной канал уведомлений в `04_features-catalog-storefront.md` §6) остаётся основным, поэтому доставка email не блокирует старт разработки, но должна быть проверена до Этапа 2 (оформление первых реальных заказов).
