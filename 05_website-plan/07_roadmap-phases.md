# Дорожная карта разработки

Разбивка на этапы так, чтобы каждый этап давал самостоятельно полезный результат, а не "недоделанный сайт". Оценки — ориентировочные трудозатраты в неделях для небольшой команды (1–2 full-stack разработчика + дизайнер частично); при разработке через CLI-агента сроки будут определяться иначе, но последовательность и зависимости остаются актуальными.

## Этап 0 — Подготовка (перед кодом)
- Зафиксировать ответы на открытые вопросы из `00_overview.md` (тариф МойСклад, платёжный провайдер, доставка, хостинг, порядок B2B).
- Настроить технического пользователя и токен доступа в МойСклад (см. `02_moysklad-integration.md` §1).
- Проверить фактический тариф МойСклад и доступность вебхуков (бесплатный тариф их не поддерживает — блокер для §Этап 2).
- Собрать недостающий контент: тексты "О нас", реквизиты, фото товаров хорошего качества (если текущих фото из соцсетей недостаточно для карточек товара).

## Этап 1 — Каркас и синхронизация каталога (MVP-фундамент)
- Инфраструктура: монорепо, Docker, CI, окружения (см. `01_tech-stack-architecture.md`).
- Схема БД и миграции (`03_database-schema.md`).
- `moysklad-client` — типизированный клиент API (auth, базовые методы, обработка лимитов/ошибок из `02_moysklad-integration.md` §3, §9).
- Полная синхронизация каталога: товары, категории, склады, цены → в локальную БД.
- Инкрементальная синхронизация остатков (`report/stock/bystore/current?changedSince=`).
- **`packages/ui-kit` — базовые дизайн-токены и первые примитивы** (кнопки, поля ввода, типографика) на основе фирменного стиля (`01_brand/brand-guidelines.md`) и первых спроектированных экранов — закладывается уже здесь, **до** начала вёрстки конкретных экранов Этапа 2, чтобы каталог/карточка товара сразу строились на общей библиотеке компонентов, а не на разовой вёрстке под один экран (важность выделена заказчиком — см. `09_workflow-tooling.md` §1б).
- **Результат этапа:** есть работающий бэкенд с актуальным кэшем каталога/остатков из МойСклад и стартовый `ui-kit`, ещё без публичного сайта.

## Этап 2 — Публичная витрина (розница)
- Каталог, карточка товара, фильтры (§`04_features-catalog-storefront.md` §1) — реализуются поверх `ui-kit` из Этапа 1; новые переиспользуемые компоненты (карточка товара, бейдж наличия, ценник) пополняют `ui-kit`, а не пишутся "по месту" в разметке страницы.
- Корзина и оформление заказа (доставка/самовывоз — доставка без агрегатора, ручной вызов Яндекс Такси/Доставки, см. `04_features-catalog-storefront.md` §2 и `06_admin-dashboard.md` §3).
- Онлайн-оплата через Сбербанк Эквайринг (`11_payment-sberbank.md`) либо "оплата при получении" как fallback на первой итерации, если интеграция платежа ещё не готова технически.
- Обратная запись заказов в МойСклад (`02_moysklad-integration.md` §7).
- Настройка вебхуков для статусов заказа (если тариф позволяет) либо запасной вариант — polling статуса раз в несколько минут.
- Базовое SEO (SSR, метатеги, sitemap).
- **Результат этапа:** сайт принимает реальные розничные заказы, они появляются в МойСклад.

## Этап 3 — Личный кабинет (розница)
- Регистрация/вход через Telegram Login Widget и VK ID/OAuth (см. `05_personal-cabinet.md` §1), история заказов, избранное, сохранённые адреса.
- Бонусная программа (интеграция с `bonusprogram` МойСклад или собственная реализация — решение зафиксировано в `05_personal-cabinet.md` §2).
- Промокоды.
- **Результат этапа:** повторные покупки и удержание клиентов поддержаны функционально.

## Этап 4 — Управленка (админ-дашборд)
- Сводка KPI, статус интеграции, остатки, заказы, клиенты (`06_admin-dashboard.md` §1–4).
- Ролевой доступ (менеджер/админ).
- **Результат этапа:** владелец получает управленческую видимость бизнеса без захода в МойСклад.

## Этап 5 — B2B / оптовый раздел
- Раздел `/opt`, оптовый прайс, заявки на доступ и их модерация (`04_features-catalog-storefront.md` §3, `05_personal-cabinet.md` §3, `06_admin-dashboard.md` §4).
- Индивидуальные условия для оптовых клиентов.
- **Результат этапа:** второе направление бизнеса «Вистерии» (опт) представлено на сайте, а не только розница.

## Этап 6 — Маркетинг, аналитика, доработки
- Расширенная аналитика воронки, отчёты по каналам (`06_admin-dashboard.md` §5).
- Подписка на регулярную доставку.
- Модуль производства/доски флориста (`06_admin-dashboard.md` §6) — опционально.
- Оптимизация производительности, доп. SEO, A/B-тесты карточек товара.

## Зависимости между этапами

```
Этап 0 (подготовка)
   │
Этап 1 (синхронизация каталога) ──► обязателен перед всем остальным
   │
Этап 2 (витрина+заказы) ──► Этап 3 (ЛК розница) ──► Этап 4 (управленка, частично параллельно с Этапом 3)
   │
Этап 5 (B2B) ──► зависит от Этапа 2–4 (переиспользует каталог, заказы, админку)
   │
Этап 6 (маркетинг/доп.) ──► надстройка поверх всего готового
```

## Критические риски, влияющие на сроки

1. **Тариф МойСклад без вебхуков** → синхронизация статусов заказов и остатков деградирует до polling — дольше по времени реакции, но не блокирует разработку (заложено как fallback в `02_moysklad-integration.md`).
2. ~~Не выбран платёжный провайдер~~ — **снято (25.08.2026):** провайдер — Сбербанк Эквайринг (`11_payment-sberbank.md`). Остаточный риск ниже, чем при незакрытом вопросе: официальная документация Сбербанка не была доступна для прямой проверки в рамках планирования (см. `11_payment-sberbank.md` §1) — нужно сверить точные параметры API с банком перед стартом Этапа 2, но это не блокирует сам план и архитектуру.
3. ~~Служба доставки не определена~~ — **снято (25.08.2026):** доставка без агрегатора, ручной вызов Яндекс Такси/Доставки менеджером — это фактически **снижает** технический риск и объём работ Этапа 2 (не нужна API-интеграция с логистической платформой), но добавляет операционную нагрузку на менеджера (ручной шаг в `06_admin-dashboard.md` §3), что стоит учитывать при оценке кадровой нагрузки, а не только кода.
4. **Качество фото товаров** — если в МойСклад/соцсетях недостаточно качественных фото для карточек, потребуется отдельная фотосъёмка — организационная задача, не техническая, но может тормозить Этап 2.
5. **Детали процесса Telegram-бота ещё не получены** — вход через Telegram Login Widget спроектирован по стандартной схеме (см. `05_personal-cabinet.md` §1), но пользователь обещал предоставить дополнительную информацию о текущей механике бота — возможна донастройка перед стартом Этапа 3.
