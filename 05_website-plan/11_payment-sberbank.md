# Интеграция оплаты — Сбербанк Эквайринг

Решение зафиксировано пользователем: платёжный провайдер/касса — **Сбербанк**. Открытый вопрос из `00_overview.md` §6 закрыт.

## 1. Источники и статус проверки

Официальная документация Сбербанка (`securepayments.sberbank.ru/wiki`) не открылась в рамках этой сессии — сайт отдаёт ошибку сертификата (self-signed certificate) при обращении как через WebFetch, так и через браузер, т.е. это ограничение самого ресурса Сбербанка в момент проверки (25.08.2026), а не сбой на нашей стороне. Технические детали ниже подтверждены по независимому источнику с реальными примерами интеграции (см. Sources в конце) и совпадают с общеизвестной, много лет стабильной схемой API интернет-эквайринга Сбербанка. **Перед стартом Этапа 2 нужно свериться с актуальной официальной документацией**, которую Сбербанк выдаёт партнёру при подключении договора эквайринга — там же будут точные боевой/тестовый URL для конкретного мерчанта.

## 2. Принцип работы (REST, form-data/JSON, синхронный редирект на страницу оплаты)

Классическая схема "Сбербанк Эквайринг" (иногда называется "Payment Gateway" / бывший "Сбербанк.Онлайн эквайринг"), REST-методы:

1. **Регистрация заказа** — `POST /payment/rest/register.do`
   Параметры: `userName`/`password` (или `token` при токен-авторизации), `orderNumber` (внутренний ID заказа сайта), `amount` (**в копейках**, не в рублях), `returnUrl` (куда вернуть покупателя после оплаты), опционально `failUrl`, `description`, `email`/`phone` покупателя.
   Ответ: `{"orderId": "...", "formUrl": "https://..."}` — `orderId` (id платежа на стороне Сбербанка) сохраняем у себя, `formUrl` — редиректим покупателя на страницу оплаты Сбербанка.

2. **Проверка статуса платежа** — `POST /payment/rest/getOrderStatus.do` (или расширенная версия `getOrderStatusExtended.do`)
   Параметры: `orderId` (полученный на шаге 1), `userName`/`password`.
   Ответ содержит `orderStatus` (числовой код: 0 — заказан/не оплачен, 1 — предавторизован, 2 — оплачен, 3 — отменён, и т.д. — точные коды свериться с актуальной документацией/личным кабинетом мерчанта) и сумму.

3. **Возврат** — `POST /payment/rest/refund.do` — для оформления возврата (актуально: цветы — товар с возможным браком/некондицией, возвраты вероятны).

## 3. Two варианта получения статуса — синхронный + callback

- **Синхронный вариант (минимальный):** после возврата покупателя на `returnUrl` сайт сам дергает `getOrderStatus.do`, чтобы узнать, прошла ли оплата (пример именно такого подхода — см. источник в конце файла).
- **Callback/notification URL (рекомендуется дополнительно):** Сбербанк поддерживает уведомление на URL мерчанта при смене статуса заказа (настраивается в личном кабинете эквайринга) — это даёт возможность узнать об оплате, даже если покупатель закрыл браузер до возврата на `returnUrl`. **Рекомендация:** не полагаться только на синхронный возврат — обязательно настроить callback и/или периодическую фоновую проверку статуса "зависших" неоплаченных заказов (аналогично паттерну отказоустойчивости из `01_tech-stack-architecture.md`).

## 4. Архитектурная интеграция с остальным планом

- Оплата — отдельный шаг **после** создания заказа на сайте (заказ уже есть в статусе `new`/`unpaid`, см. `orders.payment_status` в `03_database-schema.md`), не блокирует запись заказа в очередь на МойСклад (`02_moysklad-integration.md` §7) — заказ уходит в МойСклад независимо от факта оплаты, статус оплаты обновляется отдельно.
- **Сумма — строго в копейках** при вызове API Сбербанка; в собственной БД сайта денежные поля — `numeric(12,2)` в рублях (см. `03_database-schema.md` §7) — конвертация на границе интеграции, не хранить копейки как основной формат в БД сайта.
- `orderId` Сбербанка — отдельное поле в таблице `orders` (добавить `sberbank_order_id text, nullable`), не путать с `moysklad_order_id`.
- Обработчик callback/webhook от Сбербанка — по аналогии с приёмником вебхуков МойСклад (`02_moysklad-integration.md` §6): тонкий обработчик, кладёт событие в очередь, отвечает быстро, дедуплицирует повторные уведомления.
- **54-ФЗ (онлайн-касса):** уточнить при подключении договора эквайринга у Сбербанка, включена ли фискализация (пробитие чека) в тарифный пакет, либо нужен отдельный сервис/кассовое решение (часто банки предлагают такую опцию "из коробки" вместе с эквайрингом, но это нужно подтвердить у менеджера Сбербанка, а не предполагать) — см. также `10_pre-development-checklist.md` §2.

## 5. Что нужно получить от Сбербанка перед разработкой (дополнение к `10_pre-development-checklist.md`)

- Логин/пароль технического API-пользователя (`userName`/`password`) либо токен — выдаётся при подключении договора эквайринга.
- Тестовый (sandbox) контур для разработки — уточнить у менеджера Сбербанка, обычно предоставляется отдельно от боевого.
- Точные боевой и тестовый базовые URL API для вашего мерчанта.
- Подтверждение по фискализации (54-ФЗ) — входит ли в пакет эквайринга.
- Настройка callback-URL в личном кабинете эквайринга (укажет на webhook-приёмник sync-слоя сайта).
