## 1. Семантическое ядро

### 1.1 Методология (как это должно быть сделано по-настоящему)

Ниже — **черновая структура ядра**, собранная по бизнес-фактам «Вистерии» (`00_overview.md` §3, `02_company/company-profile.md`) и типовым паттернам ниши «доставка цветов». Это отправная точка для проектирования URL и мета-шаблонов, **не финальное ядро**. Точные частотности запросов нужно снять из Яндекс.Wordstat (https://wordstat.yandex.ru, регион — Челябинск + область) и свести в Key Collector или Excel/Google Sheets перед стартом Этапа 2, потому что:
- частотность сильно зависит от сезона (8 марта даёт кратный скачок конкретных запросов — снимать в «обычный» месяц и отдельно фиксировать сезонные пики);
- часть кластеров (особенно «соболезнования/похороны») требует деликатной проверки на уместность и тона формулировок, а не только частотности;
- реальная кластеризация по SERP (какие запросы Яндекс/Google показывают на одной и той же выдаче) надёжнее ручной группировки по смыслу — стоит прогнать финальный список через инструмент кластеризации (Just-Magic, Rush Analytics, Topvisor и т.п.) перед распределением по страницам.

Процесс сбора: 1) собрать seed-запросы (ниже) → 2) расширить через Wordstat (правая колонка "с чем ещё ищут" + похожие запросы) и подсказки Яндекс/Google → 3) собрать частотность (обязательно в кавычках `"!запрос"` для точной частоты, не только широкой) → 4) вычистить нецелевой трафик минус-словами → 5) кластеризовать по интенту и SERP → 6) сопоставить каждый кластер с конкретным URL на сайте (см. колонку «Куда ведёт» в таблицах ниже) → 7) вести таблицу как живой документ, обновлять раз в квартал и после каждого добавления новых категорий/поводов в МойСклад.

### 1.2 Минус-слова (общие, применять ко всем кластерам при сборе частотности)

`бесплатно`, `своими руками`, `оригами`, `из бумаги`, `из фетра`, `вязание`, `вязаные`, `картинки`, `фото`, `рисунок`, `для срисовки`, `скачать`, `гифка`, `открытка распечатать`, `клипарт`, `раскраска`, `обои на рабочий стол`, `игра`, `песня`, `сонник`, `значение` (для запросов типа «хризантема к чему снится» — информационный шум не по теме), `работа` / `вакансии` (если не планируется страница «Карьера»).

### 1.4 Итог для разработчика

Из таблиц выше следует прямое требование к архитектуре URL: помимо стандартных `/catalog/[category]` и `/product/[slug]`, нужен отдельный маршрут для лендингов по поводу — `/povod/[slug]` (или `/occasion/[slug]`), с собственными полями `title`/`description`/`h1`/вступительным текстом, редактируемыми не через код, а через админку/CMS-поля у категории в МойСклад или отдельную таблицу поводов в БД (см. `03_database-schema.md` — стоит добавить туда сущность `occasion_landing`, если её ещё нет). Без отдельных полей под каждый повод SEO-кластер Б попросту нечем будет закрыть.

## 2. Мета-теги — спецификация для разработчика

### 2.1 Общие правила

- **Title**: 50–60 символов (Яндекс и Google обрезают длиннее в выдаче), уникален для каждой страницы, город — обязательный элемент для транзакционных страниц («Челябинск» в title резко повышает релевантность гео-запросам), без переспама одним и тем же словом дважды.
- **Description**: 120–160 символов, не дублирует title дословно, содержит явный призыв/выгоду (цена от, доставка сегодня, самовывоз) — это не influences ранжирование напрямую, но управляет CTR в выдаче.
- **H1**: один на странице, не равен title дословно (title — для поисковика/вкладки браузера, H1 — для человека на странице), может быть чуть шире.
- Все шаблоны — динамические, собираются из данных МойСклад (название категории/товара/цена), не хардкодятся.

### 2.3 Open Graph / соцсети

Обязательно на всех страницах (важно для превью при шаринге в VK — основной канал компании, см. §6.2):
```html
<meta property="og:title" content="{title страницы}" />
<meta property="og:description" content="{description страницы}" />
<meta property="og:image" content="{фото товара / брендовая заглушка для страниц без фото}" />
<meta property="og:type" content="product" /> <!-- website на главной/категориях -->
<meta property="og:url" content="{canonical URL}" />
<meta property="og:site_name" content="Вистерия" />
<meta property="og:locale" content="ru_RU" />
```
Twitter Card не критичен для этой аудитории (площадка не используется компанией) — можно добавить `summary_large_image` по остаточному принципу, не в приоритете.

### 2.4 Canonical и правила для параметрических URL

У каталога — фасетные фильтры (цена/повод/состав/наличие, см. `04_features-catalog-storefront.md` §1), что создаёт риск дублей и «расползания» краулингового бюджета на бессмысленные комбинации URL. Правила:

- Каждая комбинация фильтров, применённая через query-параметры (`?price=1500-3000&flower=rose`), получает `<link rel="canonical" href="{URL категории без параметров}">` — то есть указывает сама на себя без фильтров.
- Единственное исключение — если конкретная комбинация «повод + состав» (например, «розы на 8 марта») выделена в собственный лендинг из §1.4 — тогда у неё каноничный URL сам на себя, а не на родительскую категорию.
- Пагинация каталога (`?page=2`): каждая страница пагинации индексируется отдельно с собственным canonical на саму себя (не на первую страницу — иначе товары со 2-й страницы выпадут из индекса), но с `title`, содержащим номер страницы, чтобы не дублировать первую страницу дословно.
- Сортировка (`?sort=price_asc`) — canonical на URL без параметра сортировки, `<meta name="robots" content="noindex, follow">` на отсортированные вариации.
- Поиск по сайту (`/search?q=...`) — `noindex, follow`.
- Страницы фильтра с нулевым результатом («в наличии сейчас» + узкий фильтр, ничего не найдено) — отдавать `noindex` динамически, не полагаться только на canonical.

### 2.5 Структурированные данные (JSON-LD)

**Организация (на всех страницах, в layout)** — `LocalBusiness`/точнее `FloristShop` (тип из схемы Schema.org, дочерний от Store/LocalBusiness), с двумя точками через `hasMap`/массив `location` или через две отдельные сущности `Organization` → `department`, если понадобится развести розницу и опт для карт (см. §6.1 про две карточки в Яндекс.Бизнес/2GIS):

```json
{
  "@context": "https://schema.org",
  "@type": "FloristShop",
  "name": "Вистерия",
  "image": "{URL логотипа}",
  "telephone": "+7-950-741-09-15",
  "email": "visteriaopt@gmail.com",
  "address": {
    "@type": "PostalAddress",
    "streetAddress": "ул. Островского, 19а",
    "addressLocality": "Челябинск",
    "addressCountry": "RU"
  },
  "openingHoursSpecification": {
    "@type": "OpeningHoursSpecification",
    "dayOfWeek": ["Monday","Tuesday","Wednesday","Thursday","Friday","Saturday","Sunday"],
    "opens": "09:00",
    "closes": "20:00"
  },
  "priceRange": "₽₽",
  "sameAs": ["https://vk.ru/visteriaopt", "https://www.instagram.com/visteria.74/"]
}
```
⚠️ Координаты (`geo.latitude/longitude`) и точное значение `openingHoursSpecification` должны **дословно совпадать** с тем, что указано в Яндекс.Бизнес и 2GIS (§6.1) — расхождение адреса/часов между картами, разметкой на сайте и реальностью — частая причина, по которой Яндекс понижает доверие к LocalBusiness-сигналам.

**Карточка товара** — `Product` + `Offer`, обязательные поля `name`, `description`, `image`, `sku` (= код товара МойСклад, для сведения с остатками), `offers.price`, `offers.priceCurrency: "RUB"`, `offers.availability` (`InStock`/`OutOfStock`/`PreOrder`, синхронизировано с реальным остатком из кэша — см. `01_tech-stack-architecture.md`, обновляется при той же ISR-ревалидации, что и сама страница, а не отдельным батчем, иначе разметка разойдётся с фактом и это триггерит ручные санкции Google за вводящую в заблуждение разметку). `AggregateRating`/`Review` добавлять **только** когда на сайте реально появятся отзывы (см. `04_features-catalog-storefront.md` §4 — сбор отзывов пока не завершён) — разметка рейтинга без реальных отзывов на странице прямо запрещена правилами Google и Яндекса.

**Категория** — `BreadcrumbList` (обязательно, недорого по разработке, ощутимо по CTR за счёт хлебных крошек в сниппете) + `ItemList` для товаров в категории. **Не** размечать категорию как единичный `Product`/`AggregateOffer` — это трактуется как спам-разметка (страница описывает много разных товаров, не один).

**FAQ (опционально, если появится страница с вопросами по доставке/оплате)** — `FAQPage`, даёт доп. место в выдаче Google в виде раскрывающихся вопросов; в Яндексе эффекта меньше, но не вредит.

Проверка перед релизом каждого типа страницы: Яндекс валидатор микроразметки (webmaster.yandex.ru/tools/microtest) и Google Rich Results Test — оба, т.к. требования расходятся в деталях.

```
Disallow: /*?sort=
Disallow: /*?page=
Allow: /

User-agent: Yandex
Disallow: /cart
Disallow: /checkout
Disallow: /account
Disallow: /admin
Disallow: /api
Disallow: /search
Clean-param: sort&price&flower&availability /catalog/

Sitemap: https://{домен}/sitemap.xml
```

Пояснения:
- `Clean-param` — директива, специфичная для Яндекса: явно сообщает, что параметры фильтра/сортировки не создают новый контент, экономит краулинговый бюджет эффективнее, чем один `Disallow` (Google эту директиву не понимает — для него достаточно canonical из §2.4).
- `/api` закрывается на уровне robots для порядка, но не полагаться на это как на защиту — API и так должно быть закрыто аутентификацией там, где нужно (см. `08_nonfunctional-security-ops.md` §1).
- Домен в директиве `Sitemap:` — финализировать после выбора хостинга/домена (открытый вопрос №5 в `00_overview.md` §6).

### 3.2 sitemap.xml

- **Генерация динамическая**, не статический файл — привязана к тем же данным, что и ISR-ревалидация каталога (`01_tech-stack-architecture.md`): при изменении цены/остатка/названия товара `lastmod` в sitemap должен обновляться реальной датой изменения, а не датой деплоя сайта — иначе Яндекс/Google быстро перестают доверять `lastmod` и просто игнорируют его как сигнал.
- **Структура**: пока каталог небольшой (десятки–сотни SKU, судя по 23+ позициям в VK на момент сбора данных, `04_research/notes.md`) — один `sitemap.xml` достаточен. Закладывать сразу генерацию **sitemap index** (`sitemap-index.xml` → `sitemap-products.xml`, `sitemap-categories.xml`, `sitemap-pages.xml`), чтобы при росте ассортимента (особенно с учётом B2B-раздела, Этап 5) не пришлось переделывать архитектуру — порог для разбивки на несколько файлов у обоих поисковиков около 50 000 URL на файл, но разделение по типу контента полезно для аналитики покрытия в Вебмастере/Search Console гораздо раньше этого порога.
- **Включать**: главная, все страницы категорий, все карточки товаров в наличии (товары, которых давно нет на складе и не планируется — исключать через `noindex`, не держать в индексе «мёртвые» карточки), лендинги `/povod/*`, `/opt`, статьи блога, статические страницы (о нас, контакты, доставка и оплата, политика конфиденциальности — да, эта тоже, она часто индексируется и это нормально).
- **Не включать**: любые URL с query-параметрами, `/cart`, `/checkout`, `/account/*`, `/admin/*`, страницы пагинации после определённого разумного предела (если категория растянута на много страниц — включать первые N, дальше полагаться на canonical-цепочку и внутренние ссылки, не sitemap).
- **Image sitemap** — отдельный смысл именно для этого бизнеса: карточки букетов — визуальный товар, трафик из Яндекс.Картинок/Google Images по запросам вида «букет роз фото» реален. Расширение `<image:image>` внутри записи товара в основном sitemap (не обязательно отдельный файл) с `<image:loc>` на фото товара из МойСклад.
- **Мониторинг**: после каждого релиза с изменением структуры URL — проверять в Яндекс.Вебмастере раздел «Индексирование → Страницы в поиске» и в Search Console «Покрытие», что не появилось резкого падения проиндексированных страниц (частый симптом сломанного canonical/robots после деплоя).

## 4. Яндекс.Метрика и Search Console

### 4.1 Порядок установки (важно — до, не после согласия на cookies)

По 152-ФЗ явное согласие пользователя требуется до загрузки аналитических счётчиков, а не постфактум формулировкой «продолжая пользоваться сайтом, вы соглашаетесь». Это напрямую стыкуется с уже зафиксированным в проекте требованием к согласию на обработку персональных данных (`08_nonfunctional-security-ops.md` §1): нужен единый cookie-баннер с явной кнопкой «Принять» и отдельной возможностью отказаться от необязательной аналитики, который **гейтит** инициализацию Метрики. Технически — Метрика инициализируется условно, только после `localStorage`/cookie-флага согласия, а не безусловным тегом в `<head>` на каждой загрузке. Политика конфиденциальности должна явно называть Яндекс.Метрику как получателя данных.

### 4.2 Яндекс.Метрика — базовая настройка

- Счётчик подключать через `next/script` со стратегией `afterInteractive` (не блокирует первую отрисовку — важно для LCP-цели из `08_nonfunctional-security-ops.md` §2), асинхронный сниппет.
- **Вебвизор + карта скроллов/кликов** — включить сразу, даёт качественные данные по UX карточки товара и чекаута без доп. разработки.
- **Цели (Goals)**, минимальный набор для старта:
  - `order_submitted` — заказ оформлен (конверсионная, привязана к ecommerce `purchase`);
  - `add_to_cart` — добавление в корзину;
  - `checkout_started` — переход к оформлению;
  - `phone_click` — клик по номеру телефона;
  - `messenger_click` — клик по Telegram/WhatsApp (если появятся отдельные контакты, см. открытый пункт в `02_company/contacts.md`);
  - `wholesale_request` — заявка на опт (`/opt`, `05_personal-cabinet.md` §3);
  - `promo_used` — применён промокод.

### 4.3 Электронная коммерция (dataLayer)

Стандарт Метрики использует `dataLayer.push()` с объектом `ecommerce`, события `detail` (просмотр товара), `add`/`remove` (корзина), `purchase` (оплаченный заказ). Обязательное правило: `id` товара в каждом событии — это **тот же код товара, что в МойСклад** (не автоинкремент внутренней БД), иначе отчёты Метрики по товарам нельзя будет свести с остатками/выручкой из МойСклад при анализе. Пример события «просмотр карточки»:

```js
dataLayer.push({
  "ecommerce": {
    "currencyCode": "RUB",
    "detail": {
      "products": [{
        "id": "{код_товара_МойСклад}",
        "name": "{название}",
        "price": "{цена}",
        "category": "{категория}",
        "brand": "Вистерия"
      }]
    }
  }
});
```
`purchase` — отправлять **после** подтверждения на стороне сервера (когда заказ реально создан, а не по факту клика «оплатить»), чтобы отменённые/неуспешные оплаты через Сбербанк Эквайринг (`11_payment-sberbank.md`) не искажали отчёт. Перед релизом проверять через `?_ym_debug=1` и отладчик dataLayer в браузере — на реальной сборке, не на моках.

Отчёты, которые становится возможно смотреть после настройки: заказы, содержимое заказов, категории/бренды, товары, брошенные корзины, промокоды — прямая база для решений вроде «какая ценовая категория и повод продаются лучше», важных именно для ассортимента флористики.

### 4.4 Яндекс.Вебмастер

- Подтверждение прав — рекомендуемый способ для этого проекта: через **HTML-файл в корне** (проще всего автоматизировать в Next.js — статический файл в `public/`) либо через **тег в Метрике** (раз счётчик уже стоит — не нужен отдельный код). DNS-способ избыточен, если нет отдельной команды, управляющей DNS-зоной.
- После подтверждения — добавить `Sitemap` (§3.2), дождаться первого обхода (до суток).
- Регулярно проверять разделы: «Диагностика сайта» (критичные ошибки), «Индексирование → Страницы в поиске» и «Исключённые страницы» (следить, чтобы там не оказались страницы товаров — если товар «исключён», значит либо `noindex` по ошибке, либо canonical указывает не туда), «Микроразметка» (валидность JSON-LD из §2.5), «Проверка мобильных страниц».
- ⚠️ **Не использовать Яндекс.Турбо-страницы** — сервис официально закрыт Яндексом с апреля 2025 года («технология потеряла актуальность» на фоне повсеместных быстрых мобильных сайтов и адаптивной вёрстки) — упоминания этого инструмента в старых гайдах уже неактуальны, отдельная турбо-версия каталога не нужна и не поддерживается.

### 4.5 Google Search Console

⚠️ На сентябрь 2026 сервис технически доступен из России без прямой блокировки (в отличие от Google Analytics/Google Ads, к которым больше вопросов регулятора, так как GSC работает с обезличенными техническими данными индексации, а не персональными данными пользователей) — но его статус не гарантирован на среднем горизонте. Рекомендация: подключить как **дополнительный**, не основной инструмент — верификация через тот же HTML-файл или DNS-запись, что и для Яндекс.Вебмастера, добавить тот же sitemap, но:
- не строить процессы, критично зависящие только от GSC (например, не делать индексацию в Google единственным способом узнавать об ошибках сканирования — Яндекс.Вебмастер должен быть основным источником);
- периодически (раз в квартал) выгружать данные о позициях/кликах в отдельный файл — на случай внезапной потери доступа к сервису.

Доля органического трафика из Google для регионального e-commerce в РФ на 2026 год ощутимо меньше, чем из Яндекса (Яндекс исторически доминирует на российском рынке поиска, особенно вне мобильного Android/Chrome-экосистемы) — поэтому весь план в этом документе приоритизирует Яндекс-инструменты, а Google-присутствие поддерживается «на всякий случай» и как задел на будущее.

## 5. Роли: что делает разработчик, что — не разработчик

| Задача | Кто отвечает |
|---|---|
| Шаблоны мета-тегов, JSON-LD, canonical-логика, sitemap/robots (§1–4) | Разработчик, один раз при разработке Этапа 2 |
| Наполнение конкретных title/description сверх шаблона (если нужно вручную поправить топ-10 самых частотных страниц) | Маркетолог/владелец через админку, без участия разработчика после того, как поле в админке появилось |
| Установка счётчиков, целей, dataLayer (§4) | Разработчик |
| Анализ отчётов Метрики, принятие решений по ассортименту/акциям на основе данных | Владелец/маркетолог |
| Регистрация в Яндекс.Бизнес, 2GIS, Google Business Profile, ведение отзывов (§6.1) | Владелец/маркетолог, не входит в объём разработки сайта |
| YML-фид для Яндекс.Маркет/VK Товары (§6.2) | Разработчик генерирует фид (техническая часть), маркетолог подключает его в кабинетах площадок |
| Ведение соцсетей, контент-план, публикации (§6.2–6.3) | Владелец/маркетолог/SMM |
| Настройка Яндекс.Директ, VK Реклама (§7) | Маркетолог или подрядчик по рекламе — отдельный от разработки бюджет и компетенция |

## 6. Продвижение

### 6.1 Локальное SEO и карты

Для локального бизнеса с физическими точками (розница на Островского, 19а; опт-склад на Ижевской, 56 — `02_company/contacts.md`) карты часто дают трафик и доверие сопоставимо с органической выдачей, а без карточек в Яндекс.Картах/2GIS сайт вообще не участвует в блоке карт над органической выдачей по гео-запросам («доставка цветов рядом», «цветочный магазин на карте»).

**Яндекс.Бизнес** (business.yandex.ru): создать организацию через Яндекс ID (рекомендуется рабочий, не личный аккаунт владельца — на случай смены сотрудника), указать точное совпадение адреса/телефона/часов работы с сайтом (см. требование к консистентности в §2.5), выбрать основную рубрику «Магазин цветов»/«Доставка цветов» + до двух дополнительных («Оптовая торговля цветами» для второй точки, если карточки разводятся). Модерация — обычно до трёх рабочих дней, после публикации организация сразу видна на Картах, в Поиске — на следующий день. Отдельный вопрос — заводить ли опт-склад на Ижевской как публичную карточку (даёт находимость B2B-клиентам по запросу «цветы оптом Челябинск рядом») или скрыть как не для розничных посетителей — ⚠️ решение за заказчиком, технически возможны оба варианта.

**2GIS**: правила размещения строже по проверке — сервис вправе запросить документы и фото вывески на входе, при этом наличие телефона/сайта — по факту обязательное условие размещения без адреса, а название организации не должно содержать акции/способы оплаты в самом наименовании (частая ошибка малого бизнеса — писать в название «Вистерия | скидка 15%», это отклоняется модерацией). Регистрация не более 5 рубрик на один адрес.

**Google Business Profile**: завести на всякий случай, статус доступности сервисов Google из РФ для бизнес-профилей нестабилен (аналогично оговорке в §4.5) — не приоритет, но и не должен быть забыт: если/когда доступность восстановится, лучше иметь готовую подтверждённую карточку, чем начинать с нуля.

**Консистентность (NAP — Name, Address, Phone)**: единая эталонная запись адреса/телефона должна быть заведена один раз (например, как поле в `03_database-schema.md` или конфиге сайта) и **дословно** копироваться в: подвал сайта, страницу контактов, JSON-LD (§2.5), Яндекс.Бизнес, 2GIS, Google Business, шапку VK-сообщества. Расхождения в написании («ул. Островского, 19а» vs «Островского д.19а») читаются поисковиками и агрегаторами как разные адреса и размывают локальный SEO-сигнал.

**Отзывы**: у компании пока нет собранной базы отзывов (`04_features-catalog-storefront.md` §4 — отзывы «нужно собрать вручную у заказчика»). Реалистичный канал сбора — тот же Telegram-бот, что уже используется для уведомлений о статусе заказа (`04_features-catalog-storefront.md` §6): через 1–2 дня после доставки отправлять сообщение с прямой ссылкой на отзыв в Яндекс.Картах/2GIS. Это одновременно решает задачу для карт (рейтинг влияет на позицию карточки в блоке карт) и для будущей `AggregateRating`-разметки на сайте (§2.5) — но по-настоящему собранные, не постановочные отзывы.

### 6.2 Соцсети

Проект уже фиксирует явную асимметрию каналов (`company-profile.md`): **VK — основная площадка** (1032 подписчика, активные продажи, велось с момента основания сообщества), **Instagram — вспомогательная** (120 подписчиков). ⚠️ Эта асимметрия, вероятно, только усилится: Instagram в России заблокирован Роскомнадзором с марта 2022 года и остаётся недоступен без VPN — держать его как «визитку»/архив контента разумно, но не стоит вкладывать в него ресурсы продвижения как в приоритетный канал привлечения новых клиентов; основной прирост трафика из соцсетей реалистично ожидать через VK.

Практические шаги для VK как канала продвижения (не входит в разработку сайта как таковую, но сайт должен технически это поддерживать):
- **VK Товары**: выгрузка каталога в формате YML-фида (тот же формат, что использует Яндекс.Маркет) — фид генерируется на основе тех же данных МойСклад, что и сам сайт (`02_moysklad-integration.md`), значит это не отдельная синхронизация, а ещё один потребитель уже существующего кэша каталога. Технически — отдельный эндпоинт `/feed.yml`, обновляемый по тому же расписанию, что и остальной кэш.
- **VK Реклама (единый кабинет)**: установка пикселя ВКонтакте на сайт для ретаргетинга посетителей, которые посмотрели карточку товара, но не купили — динамический ретаргетинг на базе тех же веб-событий, что уже размечены для Метрики (§4.3), пиксель слушает те же `detail`/`add`/`purchase` события.
- **UTM-метки** на всех ссылках из VK-постов и рекламных объявлений на сайт — обязательное условие, чтобы в Метрике (§4.2) трафик из соцсетей не схлопывался в «переходы из социальных сетей» одним блоком, а был виден по конкретным постам/кампаниям.
- Кросс-ссылки сайт ↔ VK: виджет последних постов VK на сайте (уже отмечен как «возможно» в `04_features-catalog-storefront.md` §4 — рекомендуется реализовать, не оставлять опциональным, раз VK — основной канал) и наоборот, ссылка на сайт закреплена в шапке сообщества и во всех постах с товарами.

### 6.3 Контент-маркетинг

Ключевая идея — контент должен закрывать информационный кластер Г и особенно сезонный кластер Б из §1.3, и публиковаться **заранее** относительно пиковых дат, а не в сам пиковый день (когда индексация уже не успеет отработать, а нагрузка на сайт и так максимальная — см. риск в `08_nonfunctional-security-ops.md` §5).

**Сезонный контент-календарь** (публиковать за 3–6 недель до даты):

| Дата | Тема контента |
|---|---|
| Середина января | «Букеты на 14 февраля: что выбрать заранее» |
| Начало февраля | «Букеты на 8 марта — как заказать, чтобы точно успеть» (готовить лендинг `/povod/8-marta` к этому моменту, не позже) |
| Начало августа | «1 сентября: букеты учителю и первокласснику» (уже есть акция «ШКОЛА» — контент должен на неё явно ссылаться) |
| Октябрь | «Свадебный сезон: букеты невесты, разбор стилей» |
| Ноябрь | «Новогодние композиции: что заказать заранее на праздники» |
| Круглый год, без привязки к дате | «Как ухаживать за розами/пионами/хризантемами, чтобы стояли дольше», «Сколько стоит букет в Челябинске — разбор по бюджетам», «Что означает "дофаминовый букет"» (фирменный термин компании — материал, который больше нигде не встретить, хороший кандидат на уникальность и брендовый трафик) |

**Локальный контент**: страница/блок «Зоны и стоимость доставки по районам Челябинска» — закрывает гео-длинный хвост из кластера А §1.3, но требует сначала зафиксировать саму зону и стоимость доставки (пока это открытый пункт в `02_company/company-profile.md` — «география доставки и стоимость доставки» отмечена как несобранная).

**B2B-контент** (для `/opt`, кластер Е): короткие материалы «Как мы работаем с розничными магазинами», «Прямые поставки от теплиц — что это значит для партнёра» — не столько для SEO-объёма, сколько для доверия у B2B-посетителя, который обычно сверяет несколько поставщиков перед обращением.

Организационно: ведение блога не требует от разработчика ничего сверх типовой CMS-функциональности (список статей, редактор, привязка изображений) — сам контент-план и написание текстов — задача владельца/маркетолога/копирайтера, не входит в объём Этапа 2/6 по дорожной карте (`07_roadmap-phases.md`).

## 7. Дополнительные каналы (кратко, вне ядра SEO)

- **Яндекс.Директ** — комплементарен, не замена SEO: использует то же семантическое ядро (§1) для сбора ключевых фраз, те же цели Метрики (§4.2) для оптимизации по конверсиям, особенно полезен в первые месяцы после запуска, пока органика ещё не набрала позиции, и точечно — под конкретные пиковые даты (8 марта), где органического трафика физически не хватит на весь спрос за несколько дней пика.
- **Агрегаторы доставки/маркетплейсы** — на сентябрь 2026 в проекте это открытый вопрос (в `02_company/contacts.md` явно отмечено «ссылки на агрегаторы доставки цветов, если используются» как несобранный пункт) — если заказчик подтвердит работу с такими площадками, они добавляют ещё один канал, требующий того же YML-фида, что и VK Товары (§6.2), но не заменяют SEO — это платный/комиссионный канал, а не органический.
- **Городские справочники/порталы Челябинска** — нишевые доски объявлений и городские каталоги организаций дают дополнительные внешние ссылки (влияют на доверие домена) практически бесплатно — разовая задача для маркетолога, не системный канал.
