# Интеграция с МойСклад — детальная спецификация

Источник: официальная документация [dev.moysklad.ru/doc/api/remap/1.2/](https://dev.moysklad.ru/doc/api/remap/1.2/) (JSON API 1.2), проверено вручную 25.08.2026.

## 1. Авторизация

МойСклад поддерживает два способа:

1. **Basic Auth** — заголовок `Authorization: Basic <base64(логин:пароль)>` на каждый запрос.
2. **Токен доступа (рекомендуется для сайта)** — сначала получаем токен:

```
POST https://api.moysklad.ru/api/remap/1.2/security/token
Authorization: Basic <base64(логин:пароль)>
Accept-Encoding: gzip
```
Ответ: `{"access_token": "..."}`. Дальше все запросы идут с `Authorization: Bearer <access_token>`.

⚠️ **Важно**: при генерации нового токена все ранее выданные токены пользователя отзываются — генерировать токен нужно один раз при настройке интеграции и хранить его как секрет (переменная окружения / secret manager), а не заново на каждый запуск.

**Рекомендация:** завести в МойСклад отдельного технического пользователя ("Сайт-интеграция") с ограниченными правами вместо использования личной учётки владельца — так можно точно контролировать, что может делать сайт (создавать заказы, читать остатки), и легко отозвать доступ при необходимости.

## 2. Базовые технические параметры

- **Base URL:** `https://api.moysklad.ru/api/remap/1.2/`
- Обязательный заголовок `Accept-Encoding: gzip` — без него сервер отвечает `415`.
- Формат дат: `ГГГГ-ММ-ДД ЧЧ:мм:сс` (время — московское, MSK).
- Пагинация: параметры `limit` (макс. 1000) и `offset`; в объекте `meta` при большом списке появляются `nextHref`/`previousHref`.
- Фильтрация: параметр `filter` (`field=value`, операторы `= > < >= <= != ~ ~= =~`, несколько условий через `;`).
- Сортировка: параметр `order` (`order=name` или `order=name,desc;code,asc`).
- Массовые операции (создание/обновление/удаление списком): лимит **1000 объектов за запрос**, таймаут обработки — **5 минут**.

## 3. Лимиты запросов (критично для sync-слоя)

МойСклад отдаёт состояние лимита в заголовках ответа:

| Заголовок | Смысл |
|---|---|
| `X-RateLimit-Limit` | сколько запросов можно сделать равномерно за интервал до ошибки 429 |
| `X-RateLimit-Remaining` | сколько запросов осталось до 429 |
| `X-Lognex-Retry-TimeInterval` | длительность интервала лимита, мс |
| `X-Lognex-Reset` | через сколько мс лимит сбросится |
| `X-Lognex-Retry-After` | время до сброса, мс |

При превышении — код **429**. Отдельно есть лимит на **количество одновременных (параллельных) запросов** — при превышении тоже 429, с ошибкой `1073 "Превышено ограничение на одновременное количество запросов"`.

**Архитектурный вывод:** sync-worker обязан:
1. Соблюдать backoff по заголовкам лимита (не бить API "в лоб" на полную скорость).
2. Ограничивать конкурентность собственных запросов к МойСклад (например, не более 3–5 одновременных запросов).
3. Реализовать очередь с retry (BullMQ) вместо синхронных вызовов из пользовательских запросов сайта.

## 4. Сущности МойСклад, которые участвуют в интеграции

| Сущность МойСклад | Код в API | Роль на сайте |
|---|---|---|
| Товар | `product` | Карточка товара в каталоге |
| Комплект | `bundle` | Наборы/композиции (если используются) |
| Группа товаров | `productfolder` | Категории каталога |
| Склад | `store` | 2 склада «Вистерии» — розница (Островского) и опт (Ижевская); используется для показа остатков "по складу" и самовывоза |
| Контрагент | `counterparty` | Клиент сайта (создаётся/находится по телефону при оформлении заказа) |
| Прайс-лист / Тип цены | `pricetype`, price lists | Розничная цена vs. оптовая цена для B2B-раздела |
| Заказ покупателя | `customerorder` | Заказ с сайта, ожидающий обработки менеджером |
| Отгрузка | `demand` | Финальная продажа/отгрузка (после сборки заказа) |
| Розничная продажа | `retaildemand` | Альтернатива для быстрых заказов "самовывоз сейчас" |
| Бонусная программа | `bonusprogram` | Программа лояльности личного кабинета (см. `05_personal-cabinet.md`) |
| Вебхук | `webhook` | Подписка на события изменения сущностей |

## 5. Остатки — как обеспечить «полную доступность» на сайте

МойСклад даёт три способа получить остатки, каждый — под свою задачу:

### 5.1. Отчёт «Остатки» (report/stock) — основной источник для каталога

- `GET /report/stock/all` — расширенный отчёт (детально по каждому товару: цена, изображение, себестоимость и т.д.). Тяжёлый запрос — использовать для **полной ежедневной синхронизации** каталога (ночью, по крону), не чаще.
- `GET /report/stock/all/current` — краткий отчёт, лёгкий и быстрый. Параметры:
  - `stockType=quantity|freeStock|reserve|inTransit` — что именно возвращать (физический остаток / доступно к продаже за вычетом резерва / в резерве / в пути).
  - `include=zeroLines` — включать нулевые остатки.
  - `changedSince=2026-08-23` — **инкрементальная синхронизация**: только то, что изменилось с указанного момента. Это ключевой параметр для частого опроса (каждые несколько минут) без лишней нагрузки.
- `GET /report/stock/bystore/current` — остатки **в разрезе склада** (обязательно для «Вистерии» с двумя точками — сайт должен уметь показать "в наличии для самовывоза с Островского" отдельно от оптового склада). Поддерживает `filter=assortmentId=...;storeId=...` для точечного опроса конкретных товаров/складов.
- `GET /report/stock/byslot/current` — остатки по ячейкам хранения (если в МойСклад включено ячеичное хранение; на старте, вероятно, не требуется).

**Рекомендуемая стратегия опроса:**
- Каждые **2–5 минут**: `report/stock/bystore/current?stockType=freeStock&changedSince=<последний_синк>` — быстрое обновление доступных остатков.
- Раз в сутки (ночью): полная пересборка каталога через `report/stock/all` + `entity/product` (описания, изображения, категории).
- Дополнительно — вебхуки (см. ниже) для точечной мгновенной реакции на конкретные изменения.

⚠️ Важное официальное замечание из документации: *«в отчёт попадают только товары с уже пересчитанными остатками на момент запроса; пересчёт остатков не моментальный»* — то есть при очень частых изменениях возможна секундная задержка на стороне самого МойСклад, это нужно учитывать в SLA («почти real-time», а не «мгновенно, гарантированно»).

### 5.2. Остатки в позициях документов (`fields=stock`)

При работе с заказом (`customerorder`, `demand` и др.) можно запросить `?fields=stock&expand=positions`, и в каждой позиции придёт объект:
```json
"stock": { "cost": 5000, "quantity": 999, "reserve": 90, "intransit": 9, "available": 918 }
```
Полезно для экрана менеджера "собрать заказ" в админке — видно остаток и резерв прямо в контексте заказа.

### 5.3. Вебхуки на изменение остатков

Согласно документации, помимо polling можно **подписаться на вебхуки об изменении остатков** — рекомендуется её МойСклад именно для случаев "остатки меняются часто, и нужна оперативная реакция реже, чем polling". Точный `entityType` для специализированного вебхука на остатки нужно уточнить/проверить опытным путём на этапе реализации (в документации подтверждено само наличие такой возможности, см. раздел «Отчёт Остатки» → «также можно подписаться на вебхуки на изменение остатков»); альтернативный рабочий вариант — вебхуки на `CREATE`/`UPDATE` документов, влияющих на остаток (`demand`, `supply`, `retaildemand`, `move`, `inventory`), и пересчёт затронутых товаров через `report/stock/bystore/current?filter=assortmentId=...`.

## 6. Вебхуки — общий механизм

- Сущность `webhook`, ресурс `/entity/webhook`.
- Поддерживаемые действия: `CREATE`, `UPDATE`, `DELETE`, `PROCESSED` (последнее — только для асинхронных задач).
- При создании указываются `url`, `action`, `entityType`, опционально `diffType=FIELDS` (тогда в уведомлении придёт список изменившихся полей `updatedFields`).
- **Формат уведомления:**
```json
POST https://<ваш-домен>/webhooks/moysklad?requestId=...
{
  "auditContext": { "meta": {...}, "moment": "2026-08-25 10:00:00", "uid": "employee@login" },
  "events": [
    { "meta": {"type": "product", "href": "..."}, "action": "UPDATE", "updatedFields": ["name"], "accountId": "..." }
  ]
}
```
- Сайт обязан ответить **HTTP 200 или 204 в течение 1500 мс**. При невалидном ответе — ещё 3 попытки подряд (без пауз), затем уведомление считается недоставленным и теряется безвозвратно.
- **Архитектурное требование:** webhook-приёмник должен быть максимально "тонким" — сразу положить событие в очередь (Redis/BullMQ) и ответить 200, а фактическую обработку (пересчёт остатка, обновление кэша) делать асинхронно воркером. Иначе при просадке БД/логики можно не уложиться в 1500 мс и терять события.
- Ограничение: не более **5 вебхуков** на уникальную комбинацию `entityType + action` для пользовательских интеграций.
- Идемпотентность: параметр `requestId` в URL повторной отправки не меняется — можно дедуплицировать по нему.
- **⚠️ Критичное бизнес-ограничение**: *на бесплатном тарифе МойСклад вебхуки вообще не отправляются, создавать/менять их нельзя.* Значит для полноценной real-time интеграции у заказчика должен быть платный тариф МойСклад — это нужно проверить/включить в бюджет проекта до начала разработки sync-слоя (открытый вопрос из `00_overview.md`).
- Управление вебхуками доступно только администратору аккаунта МойСклад.

## 7. Запись заказов с сайта в МойСклад

Рекомендуемый флоу оформления заказа:

1. Покупатель оформляет заказ на сайте → заказ сохраняется в собственной БД сайта со статусом `NEW` (это происходит мгновенно, независимо от доступности МойСклад — см. `01_tech-stack-architecture.md`, раздел про отказоустойчивость).
2. Задача уходит в очередь sync-worker'а: найти или создать `counterparty` (по телефону/email — использовать `filter=phone=...` для поиска существующего контрагента, чтобы не плодить дубли), затем создать `customerorder` с позициями (`positions`), привязкой к нужному `store` (розница/опт) и клиенту.
3. Для передачи `syncId` при создании — использовать сгенерированный на сайте UUID заказа как `syncId`: при сетевом сбое и повторной отправке того же запроса МойСклад не создаст дубль, а вернёт ранее созданный документ. Это защищает от двойных заказов при ретраях.
4. Статус документа в МойСклад (собран/оплачен/отгружен) синхронизируется обратно на сайт через вебхук на `UPDATE` документа `customerorder`/`demand` — обновляет статус заказа в личном кабинете покупателя и в админке.
5. Оплата: если используется онлайн-оплата на сайте (см. открытый вопрос про платёжного провайдера), факт оплаты можно отразить как вход. платёж (`paymentin`) в МойСклад через API либо просто полем `payedSum`/статусом на стороне сайта — решается при выборе платёжного провайдера.

## 8. Дополнительные поля (`attributes`)

Если потребуются нестандартные атрибуты (например, "пожелание к букету", "дата и время доставки", "адрес доставки" в структурированном виде) — МойСклад поддерживает **дополнительные поля** практически на всех документах и товарах. Их можно создать через API (`POST /entity/{type}/metadata/attributes`) и передавать значения в коллекции `attributes` при создании заказа — это позволит менеджеру видеть все детали заказа с сайта прямо в интерфейсе МойСклад, без переключения между системами.

## 9. Обработка ошибок — коды, которые обязательно обрабатывать в sync-слое

| Код | Значение | Реакция сайта |
|---|---|---|
| 401 | Неверные креды / токен отозван | Алерт в админку (см. `06_admin-dashboard.md`, статус интеграции), приостановка синка |
| 403 | Нет прав на объект | Логировать, не ретраить бесконечно |
| 409 | Объект используется, нельзя удалить | Обработка в конкретных сценариях (например, удаление контрагента) |
| 429 | Превышен лимит запросов | Backoff по `X-Lognex-Retry-After`, retry из очереди |
| 500/502/503/504 | Сбой на стороне МойСклад | Retry с экспоненциальной задержкой, сайт продолжает работать на кэше |

## 10. Резюме для «полной доступности остатков» (требование пользователя)

Комбинация:
- инкрементальный polling `report/stock/bystore/current?changedSince=...` каждые 2–5 минут,
- вебхуки на документы, влияющие на остаток, для точечной мгновенной реакции,
- локальный кэш в PostgreSQL/Redis, из которого сайт **всегда** отдаёт остатки покупателю (никогда не ждёт ответ МойСклад в момент показа страницы),
- ночная полная ресинхронизация как «исправление дрейфа» —

даёт то, что можно честно назвать «полной доступностью остатков» без риска повесить сайт из-за лимитов или недоступности МойСклад.
