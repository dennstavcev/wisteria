# Нефункциональные требования: безопасность, производительность, DevOps

## 1. Безопасность

- **Токен МойСклад** — хранить только в secret-хранилище (env-переменные на сервере / vault), никогда не в репозитории и не в клиентском коде (весь обмен с МойСклад — только с backend/sync-worker, фронтенд к МойСклад никогда не обращается напрямую).
- **Технический пользователь МойСклад** с минимально достаточными правами вместо личной учётки владельца (см. `02_moysklad-integration.md` §1).
- **Webhook-приёмник**: МойСклад не подписывает вебхуки криптографически (в документации подтверждения HMAC-подписи не найдено) — поэтому:
  - принимать вебхуки на непубличный, тяжело угадываемый URL-путь (секретный сегмент в пути);
  - валидировать структуру payload и `accountId` (должен совпадать с ожидаемым аккаунтом «Вистерии»);
  - использовать `requestId` для дедупликации повторных доставок;
  - ограничить приёмник по методу (только POST) и, по возможности, зафиксировать/проверять исходящие IP МойСклад, если производитель их публикует на момент реализации.
- **Роли и авторизация**: проверка прав на backend для каждого запроса к оптовым ценам, управленке, персональным данным — не полагаться на скрытие UI.
- **Персональные данные** (152-ФЗ, РФ): телефоны/адреса клиентов — обеспечить согласие на обработку персональных данных при регистрации (чекбокс + политика конфиденциальности), рассмотреть размещение БД на серверах в РФ.
- **Платёжные данные**: онлайн-оплата — через Сбербанк Эквайринг (см. `11_payment-sberbank.md`); данные карт на своей стороне не хранятся, оплата проходит на стороне Сбербанка (redirect на `formUrl`), сайт получает только статус платежа.
- **Авторизация**: вход через Telegram Login Widget и VK ID/OAuth (см. `05_personal-cabinet.md` §1) — паролей и SMS-кодов сайт не хранит и не обрабатывает; критично проверять подписанный хэш/токен от Telegram и валидность OAuth-токена VK на backend при каждом входе, не доверять данным от клиента без проверки.
- Стандартный веб-периметр: HTTPS everywhere, rate-limiting на публичном API (защита от подбора/спама через OAuth-эндпоинты, парсинга каталога ботами), CSRF/XSS-защита форм.
- **Доступность (a11y) — явное требование самого брендбука, не только общая практика.** Гайд (`01_brand/brand-guidelines.md`, раздел «Логотип» → «Черно-белая гамма») прямо называет чёрно-белую версию логотипа «версией сайта для слабовидящих» — то есть высококонтрастный режим отображения предусмотрен дизайнером бренда, а не додуман нами. Рекомендация: заложить в вёрстку логотипа/шапки сайта переключение на ч/б-версию (или как минимум гарантировать её наличие как fallback) при системных настройках высокого контраста/уменьшенной прозрачности браузера — небольшая, но не нулевая задача, стоит учесть на этапе вёрстки хедера.

## 2. Производительность

- Кэш остатков и каталога в Redis для самых горячих запросов (главная, топ-категории).
- ISR/SSR-кэширование страниц каталога (см. `01_tech-stack-architecture.md`) с ревалидацией при обновлении остатков/цен.
- Изображения — через CDN, в современных форматах (WebP/AVIF) с responsive-размерами.
- Целевые ориентиры: LCP < 2.5с на мобильном 4G для карточки товара и главной — стандартный порог для e-commerce, влияет и на конверсию, и на SEO-ранжирование.

## 3. Тестирование

- Unit-тесты для бизнес-логики синхронизации (расчёт остатков, идемпотентность заказов).
- Интеграционные тесты sync-worker'а против mock-сервера МойСклад API (записанные фикстуры реальных ответов, чтобы не дёргать боевой МойСклад в CI).
- E2E-тесты ключевых пользовательских сценариев (оформление заказа, оплата, вход в ЛК) — Playwright.
- Нагрузочное тестирование перед пиковыми датами (8 марта, 1 сентября, Новый год — критичные пиковые дни для цветочного бизнеса).

## 4. DevOps / эксплуатация

- CI/CD: автотесты + сборка + деплой на staging автоматически при мердже в основную ветку; деплой на prod — по ручному подтверждению.
- Инфраструктура как код (Docker Compose для старта; Terraform — если растём до нескольких серверов/managed-сервисов).
- **Бэкапы БД** — ежедневные автоматические бэкапы PostgreSQL с проверкой восстановления (не только "бэкап создаётся", но и периодическая проверка "бэкап реально восстанавливается").
- Мониторинг: аптайм публичного сайта, время ответа API, глубина очереди sync-worker'а (если очередь растёт — значит синхронизация не успевает), алерты в Telegram/почту при сбоях синхронизации с МойСклад дольше N минут.
- Логи — структурированные (JSON), с уровнями и трассировкой запроса (request id) от фронта до sync-worker'а — критично для отладки "заказ не попал в МойСклад".

## 5. Соответствие пиковой нагрузке цветочного бизнеса

Цветочный e-commerce имеет ярко выраженную сезонность (8 марта — кратный обычному трафику пик). Архитектура на очередях и кэше (см. `01_tech-stack-architecture.md`) должна быть нагрузочно протестирована именно под сценарий "всплеск заказов в течение нескольких часов", а не под усреднённую дневную нагрузку.

## 6. Доступность (accessibility)

- Базовые требования WCAG 2.1 AA для витрины — контраст текста (с учётом фирменных цветов «Вистерии», см. `06_admin-dashboard.md` §9 про контраст), навигация с клавиатуры, alt-тексты изображений товаров.
