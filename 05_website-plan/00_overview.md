# План разработки сайта «Вистерия» — обзор

Дата: 25.08.2026. Статус: план для последующей разработки в CLI (документ является техническим заданием/контекстом, код в рамках этой сессии не пишется).

## 1. Что строим

Полноценный продуктовый продающий сайт цветочного магазина/оптового поставщика «Вистерия» (Челябинск) с глубокой интеграцией с учётной системой **МойСклад** (https://dev.moysklad.ru/). Это не витрина-визитка, а рабочий e-commerce продукт с четырьмя крупными частями:

1. **Витрина (storefront)** — каталог, карточки товаров, корзина, оформление заказа, доставка/самовывоз, промо и бонусы.
2. **Интеграция с МойСклад** — двусторонняя синхронизация: остатки/цены/товары идут из МойСклад на сайт, заказы с сайта уходят в МойСклад как документы.
3. **Личный кабинет** — для розничных покупателей и отдельно для оптовых (B2B) клиентов, с учётом того, что «Вистерия» реально ведёт оба направления (см. `02_company/company-profile.md`).
4. **Админ-дашборд («управленка»)** — экран статистики и управления для владельца/менеджера: продажи, остатки, заказы, клиенты, состояние интеграции.

## 2. Почему так сложно — обоснование объёма

Пользователь прямо поставил задачу «максимально усложнить» в рамках: интеграция с МойСклад + полная доступность остатков + управленческий дашборд + личный кабинет + «максимально продуктовый продажный сайт». Это фактически заказ на постройку интернет-магазина уровня «средний+ e-commerce», а не лендинга. План учитывает это и закладывает архитектуру, которая выдержит рост (несколько складов, опт+розница, бонусная программа, аналитика).

## 3. Ключевые бизнес-факты, влияющие на архитектуру

Из собранного контекста компании (`02_company/company-profile.md`, `03_social-media/`):

- **Два направления бизнеса**: розница (букеты, готовые композиции) и опт (поставка цветов другим цветочным магазинам напрямую от теплиц). Это значит на сайте нужны **два разных прайса/каталога** и, вероятно, отдельный вход для B2B-клиентов.
- **Два физических адреса** = минимум два склада в терминах МойСклад (сущность `store`): розничная точка (Островского, 19а) и оптовый склад (Ижевская, 56). Остатки нужно уметь показывать в разрезе склада (самовывоз «что есть здесь и сейчас»).
- **Быстро меняющийся ассортимент** (цветы — скоропортящийся товар, «Поставка 7 дней в неделю») → остатки должны обновляться близко к реальному времени, нельзя полагаться на редкий батч-синк раз в сутки.
- **Ценовые сегменты уже есть** (до 1500 / 2000–3000 / 3000–4000 / 4000–5000 / 5000+) — естественная структура фильтров каталога.
- **Бренд** уже имеет полностью готовый фирменный стиль (шрифты Bergamasco/Caviar Dreams, цвета #366729 / #9556B4, узор-паттерн) — см. `01_brand/brand-guidelines.md`. Дизайн сайта должен строиться на этих активах, а не придумываться заново.
- **Соцсети как канал** — VK (1032 подписчика, активные продажи) и Instagram (120 подписчиков) уже используются для приёма заказов; сайт должен дополнять, а не конкурировать (см. точки интеграции в `04_features-catalog-storefront.md`).

## 5. Ключевые архитектурные решения (кратко, подробности — в соответствующих файлах)

- **МойСклад — источник истины по товарам, остаткам, ценам и заказам.** Сайт не хранит "параллельную бухгалтерию" — он кэширует данные МойСклад для скорости и пишет туда же заказы.
- **Локальная БД как read-кэш + операционные данные сайта** (пользователи, сессии, избранное, аналитика, логи синхронизации) — обязательна, потому что дергать МойСклад API на каждый просмотр страницы каталога недопустимо (лимиты запросов, задержки). Подробности лимитов — в `02_moysklad-integration.md`.
- **Гибридная синхронизация**: вебхуки МойСклад (при платном тарифе) для мгновенной реакции + периодический polling отчёта об остатках как страховка (вебхуки в МойСклад не гарантируют доставку "во что бы то ни стало" — при неудаче уведомление удаляется без повторной попытки после исчерпания ретраев).
- **Заказ с сайта → документ в МойСклад** (Заказ покупателя / Розничная продажа), с обратной синхронизацией статуса (оплачен/собран/отгружен) на сайт через вебхуки на изменение документа.
- **Отдельные роли доступа**: Гость → Розничный клиент → Оптовый клиент (после одобрения) → Менеджер → Администратор. Управленка и часть B2B-функций требуют серверной проверки прав, а не просто скрытия кнопок на фронте.

## 6. Важные открытые вопросы к заказчику

Прежде чем переходить к реализации в CLI, стоит зафиксировать ответы (в плане ниже приняты рабочие допущения по умолчанию, отмеченные значком ⚠️):

1. Есть ли уже действующий аккаунт МойСклад и на каком он тарифе? (От этого зависит доступность вебхуков — на бесплатном тарифе МойСклад вебхуки не работают вообще, см. `02_moysklad-integration.md`.)
2. ~~Какой платёжный провайдер использовать~~ — **Решено (25.08.2026): Сбербанк Эквайринг.** Подробная техническая спецификация — `11_payment-sberbank.md`.
3. ~~Нужна ли интеграция со службами доставки~~ — **Решено (25.08.2026): своя доставка без агрегатора.** Курьер вызывается вручную через Яндекс Такси/Яндекс Доставку под конкретный заказ (без API-интеграции с логистической платформой) — см. `04_features-catalog-storefront.md` §2 и `06_admin-dashboard.md` §3.
4. Открывать ли оптовый B2B-раздел сразу в первой версии, или сначала розница, потом опт вторым этапом?
5. Где размещать сайт (хостинг/сервер) — есть ли предпочтения или ограничения?

Дополнительно решено (25.08.2026): **вход в личный кабинет — через Telegram и VK** (Telegram Login Widget + VK ID/OAuth), а не по SMS-коду, как предполагалось ранее — см. `05_personal-cabinet.md` §1. У компании уже есть Telegram-бот; детали его текущего процесса пользователь предоставит дополнительно (см. `09_workflow-tooling.md` §1а).
