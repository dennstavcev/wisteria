# Личный кабинет

Два разных профиля пользователя с общей базой (роль `role` в таблице `users`, см. `03_database-schema.md`): **розничный клиент** и **оптовый (B2B) клиент**. Плюс служебные роли `manager`/`admin`, у которых личный кабинет не нужен — у них вход в `06_admin-dashboard.md`.

## 1. Регистрация и вход

**Решение зафиксировано пользователем (25.08.2026): вход через Telegram и VK, без SMS.** Ранее в плане предполагался вход по номеру телефона + SMS-код — заменено.

- **Telegram Login Widget** — стандартный виджет Telegram для входа на сайт: пользователь авторизуется через свой Telegram-аккаунт, сайт получает `id`, `first_name`, `username`, `photo_url` и подписанный хэш, проверяемый секретом бота (`bot token`). У «Вистерии» уже есть собственный Telegram-бот — Login Widget привязывается к тому же боту (тот же `bot token`), отдельный бот для авторизации не нужен. **Пользователь предоставит дополнительную информацию о текущей механике/процессе бота** — до получения этих деталей раздел ниже фиксирует стандартную схему Telegram Login Widget как рабочее допущение ⚠️, возможно потребуется уточнение после получения информации о боте (см. также `09_workflow-tooling.md`).
- **VK ID / VK OAuth** — вход через ВКонтакте (у компании есть активная группа VK, см. `03_social-media/vk.md`, — аудитория уже там). Требует регистрации приложения VK (получение `client_id`/`client_secret` — см. `10_pre-development-checklist.md`).
- Оба варианта не требуют хранения паролей и SMS-шлюза — идентификация происходит через OAuth-провайдера (Telegram/VK), сайт хранит только `telegram_id`/`vk_id` и данные профиля, отданные провайдером (см. `03_database-schema.md` §2, поля `telegram_id`, `vk_id`, `auth_provider`).
- Номер телефона по-прежнему запрашивается — но не как логин, а как контактные данные для координации доставки (курьер должен дозвониться, см. `06_admin-dashboard.md` §3) и для связи с контрагентом в МойСклад.
- При первом заказе можно оформить как гость, с предложением "войти через Telegram/VK — сохранить данные" (снижает трение при первой покупке).
- При создании аккаунта — привязка/создание контрагента (`counterparty`) в МойСклад; идентификатор связи — `telegram_id`/`vk_id` + номер телефона (если указан), чтобы история покупок в МойСклад и на сайте не расходилась.
- **Технический плюс данного подхода:** т.к. у «Вистерии» уже есть Telegram-бот, тот же канал можно использовать не только для входа, но и для уведомлений о статусе заказа (см. `04_features-catalog-storefront.md` §6) — единая точка контакта с клиентом вместо отдельного SMS-канала.

## 2. Розничный личный кабинет

- **История заказов** со статусами (синхронизированными из МойСклад, см. `02_moysklad-integration.md` §7) — новый / собирается / в пути / доставлен.
- **Повтор заказа** в один клик (актуально для регулярных покупателей — корпоративные секретари, заказывающие цветы на все праздники).
- **Избранное** (список товаров).
- **Сохранённые адреса доставки**.
- **Система лояльности и статистика покупок** — см. подробный разбор в §2.1 ниже (отдельный акцент по требованию заказчика).
- **Подписка на регулярную доставку цветов** ("букет каждую пятницу") — не нативная функция МойСклад, реализуется на сайте как отложенные заказы, создаваемые по расписанию (cron → создание `customerorder` в нужную дату).
- Управление уведомлениями (Telegram-бот/email — см. §1: Telegram уже является каналом входа, логично использовать его же для уведомлений вместо отдельного SMS-канала).

### 2.1. Система лояльности и статистика покупок клиента (ключевое требование)

Прямое требование заказчика: в личном кабинете клиент должен наглядно видеть **сколько он купил** (историю и сумму покупок) и **сколько у него бонусов**. Это не просто "список заказов", а отдельный экран/блок ЛК, спроектированный как мини-дашборд для клиента.

**Что показывает экран лояльности клиента:**

| Элемент | Источник данных | Комментарий |
|---|---|---|
| Текущий баланс бонусов | `users.bonus_points_cache` (зеркало МойСклад `bonusprogram` или собственный расчёт — см. ниже) | Крупно, на видном месте — как баланс на карте лояльности |
| Сколько всего потрачено (сумма покупок, ₽) | Агрегат по `orders` клиента: `SUM(total) WHERE user_id = ... AND status IN (доставлен, оплачен)` | «Всего с нами: 47 500 ₽» — накопительная сумма за всё время |
| Количество заказов | `COUNT(orders)` по клиенту | «14 заказов» |
| Средний чек клиента | `AVG(orders.total)` по клиенту | Полезно и клиенту (осознание своих трат), и для персонализации |
| История начислений/списаний бонусов | `bonus_transactions` (дата, заказ, +/− баллов, причина: "начислено за заказ №123" / "списано при оплате заказа №130" / "приветственный бонус") | Аналог выписки по бонусной карте — прозрачность важна для доверия к программе |
| Статус/уровень (опционально, вторая волна) | Пороги по накопленной сумме покупок (например, "Клиент", "Постоянный клиент", "VIP" при разных суммах) | Не нативно в МойСклад — логика уровней реализуется на сайте поверх агрегата суммы покупок |
| Прогресс до следующего уровня/бонуса (опционально) | Расчёт на основе порогов уровней | Геймификация — повышает вовлечённость, но не блокирует MVP |

**Реализация балансов баллов — два варианта (см. также `02_moysklad-integration.md`):**
- **(а) Нативная сущность МойСклад `bonusprogram`** — курс начисления/списания баллов, приветственные баллы при регистрации или первой покупке уже поддержаны "из коробки" в API МойСклад. Баланс баллов на сайте — зеркало значения из МойСклад, подтягивается при синхронизации контрагента.
- **(б) Полностью собственная реализация** (таблица `bonus_transactions` в `03_database-schema.md`) — нужна, если требуется более гибкая логика, чем позволяет стандартная бонусная программа МойСклад (например, уровни лояльности, сгорание баллов по своим правилам, начисление за действия, не связанные с покупкой — отзыв, день рождения).
- **Рекомендация:** начать с (а) для базового начисления/списания при покупке (меньше кода, стандартный механизм), и **добавить (б)** как надстройку именно для истории/детализации транзакций и будущих уровней лояльности — таблица `bonus_transactions` в любом случае нужна на сайте, чтобы красиво показать клиенту историю движения баллов (МойСклад отдаёт только текущий баланс, а не витрину истории для клиента).

**Технические требования к схеме БД** (дополнение к `03_database-schema.md`):
- В таблице `orders` уже есть поле `total` — этого достаточно для агрегатов "сколько купил"; агрегирующий запрос по клиенту должен быть либо материализован (напр. отдельная колонка `users.lifetime_spent`, обновляемая триггером/при каждом завершённом заказе), либо считаться on-the-fly с кэшированием на несколько минут — не гонять тяжёлый `SUM/COUNT` по всем заказам при каждом открытии ЛК.
- Таблица `bonus_transactions`: `id, user_id, order_id (nullable), amount (+/-), reason (enum: purchase_earn, purchase_redeem, welcome_bonus, manual_adjustment, expired), balance_after, created_at`. Поле `balance_after` — снапшот баланса на момент операции, чтобы не пересчитывать историю каждый раз.
- Эти данные также используются в управленке (`06_admin-dashboard.md`) — там менеджер видит то же самое, но по всем клиентам сразу (сегментация, топ по сумме покупок, ручная корректировка баллов).

**UI-требование к дизайну** (см. `09_workflow-tooling.md`): экран лояльности в ЛК — приоритетный экран для проектирования наравне с каталогом и корзиной, так как это прямое требование заказчика к продукту, а не второстепенная функция.

## 3. Оптовый (B2B) личный кабинет

- **Заявка на оптовый доступ** — форма (название компании, ИНН, объём закупок) → попадает в `wholesale_status = pending`, менеджер одобряет вручную в админке (см. `06_admin-dashboard.md`).
- После одобрения — доступ к оптовому прайсу и разделу `/opt` (см. `04_features-catalog-storefront.md` §3).
- **Персональные условия** — возможность у менеджера выставить индивидуальную скидку/прайс конкретному оптовому клиенту (через `pricetype`/скидки МойСклад, привязанные к конкретному контрагенту).
- **Статистика закупок** (тот же принцип, что в §2.1 для розницы) — суммарный объём закупок за период, количество отгрузок, средняя сумма отгрузки; на основе этих данных менеджер может пересматривать персональные условия/скидку.
- **Повторные регулярные заказы** — B2B-клиенты (другие цветочные магазины) обычно заказывают по графику; полезен функционал "шаблон заказа" (сохранённая корзина с типовым набором позиций).
- **История взаиморасчётов** — остаток задолженности/предоплаты, если ведётся отгрузка с отсрочкой платежа (данные тянутся из МойСклад — баланс по контрагенту).
- Выгрузка счетов/накладных в PDF (МойСклад формирует печатные формы документов — можно проксировать ссылку на печатную форму документа).
