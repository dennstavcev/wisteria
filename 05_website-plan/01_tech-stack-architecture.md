# Архитектура и технологический стек

## 1. Общая схема системы

```
                         ┌─────────────────────────┐
                         │        МойСклад          │
                         │  (источник истины: товары,│
                         │  остатки, цены, заказы)   │
                         └───────────┬──────────────┘
                     JSON API 1.2    │   Webhooks (POST)
                (Bearer/Basic auth)  │   на изменение сущностей
                                     ▼
                    ┌───────────────────────────────┐
                    │      Integration Layer         │
                    │  (sync-service, отдельный      │
                    │  процесс/воркер)                │
                    │  - webhook receiver             │
                    │  - polling-джобы (cron)          │
                    │  - очередь задач (queue)         │
                    └───────────┬───────────────────┘
                                 │ пишет/читает
                                 ▼
                    ┌───────────────────────────────┐
                    │        PostgreSQL (основная БД) │
                    │  - кэш каталога и остатков       │
                    │  - пользователи, заказы, сессии  │
                    │  - аналитика, логи синка          │
                    └───────────┬───────────────────┘
                                 │
                 ┌───────────────┴────────────────┐
                 ▼                                 ▼
     ┌─────────────────────┐          ┌─────────────────────────┐
     │   Backend API        │          │   Admin/BFF слой          │
     │  (REST/GraphQL)       │          │  для дашборда управленки  │
     └───────────┬───────────┘          └───────────┬─────────────┘
                 ▼                                     ▼
     ┌─────────────────────┐          ┌─────────────────────────┐
     │  Публичный сайт        │          │   Админ-панель              │
     │  (витрина + ЛК)        │          │   (управленка)               │
     └─────────────────────┘          └─────────────────────────┘
```

Ключевая идея: **сайт никогда не обращается к МойСклад API напрямую из пользовательского запроса**. Всё, что видит покупатель (каталог, остатки, цены), читается из собственной БД, которую в фоне поддерживает Integration Layer. Это единственный способ соблюсти лимиты МойСклад (см. `02_moysklad-integration.md`, раздел «Лимиты запросов») и дать сайту стабильную скорость независимо от состояния МойСклад.

## 2. Рекомендуемый стек

| Слой | Технология | Обоснование |
|---|---|---|
| Frontend (витрина + ЛК) | **Next.js (React, TypeScript)**, SSR/ISR для карточек товаров | SEO важен для цветочного магазина (люди ищут "доставка цветов Челябинск"), Next даёт SSR из коробки; ISR позволяет держать каталог "почти realtime" без перегенерации всего сайта |
| Backend API | **Node.js + NestJS (TypeScript)** | Единый язык с фронтом упрощает разработку и типизацию (общие DTO/схемы); NestJS даёт модульную структуру, удобную для большого количества доменов (каталог, заказы, ЛК, админка, интеграция) |
| Admin-панель (управленка) | Отдельное SPA на **React (Vite)** внутри той же кодовой базы (монорепо) либо раздел Next.js за отдельным поддоменом `admin.` | Разделение публичного трафика и внутреннего инструмента — проще ограничить доступ и не тянуть в бандл витрины админский код |
| База данных | **PostgreSQL 16** | Надёжная реляционная БД, отлично подходит для каталога+заказов+аналитики; поддержка JSONB для гибкого хранения "сырых" данных МойСклад |
| Кэш / очереди | **Redis** + **BullMQ** (очереди задач на Node) | Redis — кэш горячих данных (остатки, сессии), BullMQ — очередь для синхронизации с МойСклад, отправки писем/уведомлений, генерации отчётов |
| Синхронизация с МойСклад | Отдельный воркер-процесс (тот же монорепо, отдельный deployable) | Изоляция: сбои/лаги интеграции не должны влиять на отдачу страниц сайта |
| Файлы/изображения товаров | **S3-совместимое хранилище** (Yandex Object Storage / Selectel S3) + CDN | Изображения товаров тянутся из МойСклад (поле `image`) и кэшируются в объектном хранилище, чтобы не зависеть от доступности МойСклад при показе сайта |
| Поиск по каталогу | Встроенный полнотекстовый поиск PostgreSQL (`tsvector`) на старте; вырасти до **Meilisearch/Typesense**, если понадобится фасетный поиск | Не усложнять на старте, но заложить архитектурно точку роста |
| Платежи | **Сбербанк Эквайринг** (REST: `register.do`/`getOrderStatus.do`/`refund.do`, см. `11_payment-sberbank.md`) | Провайдер зафиксирован заказчиком (25.08.2026) |
| Контейнеризация | **Docker + docker-compose** для локали, единый образ на прод | Упрощает CLI-разработку и деплой |
| CI/CD | **GitHub Actions / GitLab CI** — lint → tests → build → deploy | Автоматизация — обязательна при таком объёме функциональности |
| Мониторинг/логирование | **Sentry** (ошибки) + структурированные логи (pino) + дашборд метрик (Grafana/Prometheus или облачный аналог) | Критично для интеграционного слоя — нужно видеть, когда синхронизация с МойСклад "просела" |

> ⚠️ Стек — рекомендация по умолчанию, оптимальная под требования (SEO, много бизнес-логики, TypeScript-монорепо). Если у вас есть предпочтение по языку/фреймворку (например, Python/Django, PHP/Laravel, 1С-Битрикс) — план функциональности ниже не привязан к конкретному стеку и легко адаптируется, но структура интеграционного слоя и БД останется актуальной.

## 3. Монорепозиторий — предлагаемая структура

```
visteria-website/
├── apps/
│   ├── web/                 # Next.js — витрина + личный кабинет
│   ├── admin/                # React/Vite — управленка
│   ├── api/                  # NestJS — основной backend API
│   └── sync-worker/          # Node-процесс — интеграция с МойСклад
├── packages/
│   ├── db/                   # схема БД, миграции (Prisma/Drizzle), общие типы
│   ├── moysklad-client/      # типизированный клиент JSON API 1.2 (переиспользуется api + sync-worker)
│   ├── ui-kit/                # общие React-компоненты и дизайн-токены — собираются из shadcn и красятся токенами «Вистерии»; см. `09_workflow-tooling.md` §1б — заказчик выделил это как отдельный важный участок работы, не второстепенная задача
│   └── shared-types/          # общие DTO/enum между frontend/backend
├── infra/
│   ├── docker/
│   └── ci/
└── docs/                       # копия/расширение этого плана для разработчиков
```

## 4. Топология окружений

| Окружение | Назначение |
|---|---|
| **local** (docker-compose) | Разработка, локальная БД, mock МойСклад для тестов |
| **staging** | Полная копия прод-архитектуры, подключена к тестовому аккаунту МойСклад (если МойСклад даёт sandbox/пробный аккаунт) или к боевому аккаунту с осторожными правами |
| **production** | Боевой сайт + боевой аккаунт МойСклад |

## 5. Ключевой принцип отказоустойчивости

Если МойСклад временно недоступен (502/503/504 — предусмотренные официальные коды ошибок API) или исчерпан лимит запросов (429) — **сайт продолжает работать** на последних синхронизированных данных из своей БД, только помечает в админке "данные могли устареть с ЧЧ:ММ". Оформление заказа в этом случае уходит в очередь (BullMQ) и отправляется в МойСклад при восстановлении связи — это критично для скоропортящегося товара (цветы), где нельзя просто "потерять" заказ.
