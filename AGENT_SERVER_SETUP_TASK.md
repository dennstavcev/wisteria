# Задание для агента: подготовка production-сервера «Вистерии» по SSH

Дата создания задания: 2026-09-01
Кому адресовано: Claude-сессии, подключённой по SSH к серверу Beget (1 vCPU / 1 GB RAM / 10 GB SSD на момент написания)
Область задания: **только подготовка сервера** (Docker, безопасность, каталоги, лимиты под маленькие ресурсы) — деплой самого сайта Wisteria в это задание не входит, см. «Где твоя зона ответственности заканчивается» ниже.

Это задание объединяет исходный `SERVER_SETUP_RUNBOOK.md` (пошаговая настройка) и `13_server-capacity-and-services-plan.md` (поправки под 1 ГБ RAM и апгрейд у Beget) в один исполняемый чек-лист, специально переписанный для агента с прямым доступом к shell, а не для человека, копирующего команды вручную.

## 0. Кто ты и что тебе нужно знать про этот сервер

Ты подключён по SSH к боевому серверу, на котором в перспективе будет жить сайт цветочной компании «Вистерия» на Next.js/NestJS/PostgreSQL/Redis, а в будущем — ещё сервисы учёта остатков и программы лояльности на отдельных поддоменах. Сервер маленький (1 ГБ RAM, 10 ГБ диска), но у хостера (Beget) конфигурацию можно увеличивать из панели управления без пересоздания сервера — только в бо́льшую сторону, обратно уменьшить нельзя. Апгрейд делает пользователь сам в панели Beget, это не твоё действие и не то, что можно сделать по SSH.

## 1. Жёсткие правила — не нарушать ни при каких обстоятельствах

1. **Одна команда за раз.** Выполнил — реально прочитал вывод — только потом следующая команда. Никогда не предполагай успех, которого не видел в выводе.
2. **При любой ошибке — стоп.** Ничего не «чинить наугад» подбором случайных команд. Опиши пользователю, что произошло (вывод команды, без паролей/токенов/ключей), и жди решения.
3. **Никогда не разрывай единственный работающий способ входа**, пока новый способ (новый пользователь, новый ключ, новый порт) не подтверждён рабочим **в отдельной, ещё открытой сессии**. Если это соединение — единственное, что у тебя есть, потеря доступа может быть необратима без консоли хостера.
4. **Не включай UFW**, пока не убедился, что реальный SSH-порт явно разрешён правилом (`sudo ufw show added` перед `sudo ufw enable`, порт должен присутствовать в списке).
5. **Не отключай `PasswordAuthentication`/`PermitRootLogin`**, пока вход по ключу не проверен рабочим в новой сессии.
6. **Никогда не выполняй `sudo usermod -aG docker <пользователь>`** — членство в группе `docker` эквивалентно root-доступу (runbook §3.5). Все Docker-команды — только через `sudo`.
7. **Секреты никогда не печатать в чат целиком и не сохранять вне `/etc/wisteria/.../` с правами `0600`/владельцем root.** Если нужно сгенерировать секрет — сгенерируй (`openssl rand -hex 32`), сохрани куда положено, но пользователю подтверди только факт создания, не значение.
8. **Не собирай Docker-образы на сервере** (`docker compose build`/`docker build`) — на 1 ГБ RAM сборка Next.js/NestJS почти гарантированно упадёт по памяти или займёт единственное ядро на долгое время. Образы собираются только в CI.
9. **Не клонируй репозиторий сайта и не пытайся развернуть приложение.** В `website_visteria` пока нет production Dockerfile/Compose/CI — это официальный блокер из runbook §10. Твоя задача заканчивается на подготовке сервера, а не на первом деплое приложения.
10. **Перед reboot или любым изменением, способным оборвать уже живой продовый трафик** — если сайт уже принимает реальные заказы, спроси пользователя и дождись подтверждения. Пока сайта ещё нет (текущая ситуация) — можно идти по чек-листу без паузы на каждом шаге, но обязательно отчитываться после каждого раздела.
11. **Если чего-то не хватает для шага** (например, ещё не готов публичный ключ CI/CD для пользователя `deploy`, или не решён вопрос про Redis сразу/отложенно) — пропусти шаг, отметь его как «ожидает решения пользователя», и иди дальше по чек-листу, а не выдумывай значение самостоятельно.

## 3. Шаг 1 — подтвердить, что Docker реально работает

```bash
sudo docker run --rm hello-world
```
Ожидается текст «Hello from Docker!». Контейнер удалится сам.

```bash
sudo docker version
```
Клиент и сервер должны ответить без ошибок.

```bash
sudo docker compose version
```
Должен быть Compose **plugin** (`docker compose`), не отдельный старый `docker-compose`.

Если что-то из этого не прошло — стоп, это блокер для всего остального (правило 2).

## 4. Шаг 2 — инвентаризация сервера

Выполни по одной и реально прочитай вывод каждой:

```bash
whoami
id
ip -brief address
sudo ss -lntup
sudo sshd -T | grep '^port '
df -hT
free -h
nproc
timedatectl
```

После вывода `free -h`/`df -hT`/`nproc` — сравни с бюджетом из `13_server-capacity-and-services-plan.md` (разделы про память и диск) и явно сообщи пользователю: реальные цифры совпадают с заявленными 1 CPU/1 GB/10 GB или отличаются, и если отличаются — в какую сторону. Это важно: часть решений по объёму RAM/диска в дальнейшем плане опирается именно на реальные, а не номинальные цифры.

Отдельно зафиксируй и сообщи пользователю: фактический SSH-порт (из `sshd -T`), и подтверди, что `5432`, `6379`, `3000`, `3001` не видны как слушающие наружу в `ss -lntup` (на этом этапе они и не должны быть, приложение ещё не развёрнуто — просто проверь, что ничего постороннего не слушает).

Целевой timezone для системных логов — `Europe/Moscow`, если `timedatectl` показывает другое — сообщи пользователю и не меняй самостоятельно без подтверждения (влияет на интерпретацию логов и cron).

## 5. Шаг 3 — своп-файл (обязателен на 1 ГБ RAM)

Это не про производительность, а про защиту от OOM-killer в момент кратковременного всплеска памяти, пока сервер маленький:

```bash
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
sudo sysctl vm.swappiness=10
```

Проверь результат:
```bash
free -h
```
В выводе должна появиться строка `Swap` с ~2.0G.

## 6. Шаг 4 — лимит логов Docker

До запуска любых контейнеров (кроме уже выполненного теста `hello-world`) настрой ротацию логов, иначе на 10 ГБ диска логи одного упавшего в цикл контейнера способны съесть всё свободное место:

```bash
sudo mkdir -p /etc/docker
```

Создай/отредактируй `/etc/docker/daemon.json` с содержимым:
```json
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}
```

Если файл уже существует и содержит другие ключи — **не перезаписывай его целиком**, аккуратно добавь эти два ключа к существующему JSON (прочитай текущее содержимое первой командой, затем отредактируй, сохраняя остальное).

```bash
sudo systemctl restart docker
```
Проверь, что Docker поднялся:
```bash
sudo systemctl status docker --no-pager
```

## 7. Шаг 5 — безопасный административный доступ

**Не отключай текущий способ входа, пока новый не проверен в отдельной, ещё открытой сессии.**

```bash
ls -la ~/.ssh
```
Публичный ключ можно показать пользователю, приватный — никогда.

Создай пользователя деплоя (имя фиксировано — `deploy`):
```bash
sudo adduser --disabled-password --gecos '' deploy
```
Пользователь `deploy` **не** добавляется в группу `docker` и не получает полный `sudo` (правило 6 выше). Позже ему можно разрешить только конкретный root-owned deploy-скрипт через узкое правило `sudoers` — это отдельная задача, не делай её сейчас без явного запроса пользователя.

```bash
sudo install -d -m 0700 -o deploy -g deploy /home/deploy/.ssh
```

Публичный ключ CI/CD для записи в `authorized_keys` пользователя `deploy` должен прислать пользователь отдельно (это не то, что ты можешь сгенерировать сам — приватная часть должна остаться в CI, никогда на сервере). **Если ключа ещё нет — спроси пользователя и переходи к следующему шагу, не блокируясь на этом.**

После того как ключ получен и записан — проверь вход в **новой** SSH-сессии под `deploy`, и только после подтверждения переходи к следующему пункту.

Усиление SSH — drop-in `/etc/ssh/sshd_config.d/99-wisteria.conf`:
```text
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
MaxAuthTries 3
LoginGraceTime 30
X11Forwarding no
AllowTcpForwarding no
AllowAgentForwarding no
```
Если для административной работы понадобится SSH-туннель — уточни у пользователя до применения `AllowTcpForwarding no`.

Перед reload — обязательная проверка:
```bash
sudo sshd -t
```
Только при пустом успешном выводе:
```bash
sudo systemctl reload ssh
```
После reload — открой **новую** SSH-сессию и подтверди, что вход по ключу работает, прежде чем считать шаг выполненным.

## 8. Шаг 6 — firewall и защита от перебора

```bash
sudo apt install -y ufw fail2ban
```

Сначала разреши **реальный** SSH-порт (из шага 4, `sshd -T`). Если порт стандартный 22:
```bash
sudo ufw allow 22/tcp comment 'SSH'
```
Если порт нестандартный — подставь фактический номер.

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 80/tcp comment 'HTTP ACME redirect'
sudo ufw allow 443/tcp comment 'HTTPS'
```

**До включения** проверь:
```bash
sudo ufw show added
```
Убедись, что SSH-порт присутствует в списке. Только после этого:
```bash
sudo ufw enable
```
Проверка:
```bash
sudo ufw status verbose
```

Помни: опубликованные Docker-порты могут обходить UFW. Приложения на этом сервере ещё не развёрнуты, но когда дойдёт до этого — PostgreSQL/Redis/backend/frontend не публикуются на `0.0.0.0` в production Compose (это уже задание не для этого шага, просто держи в уме).

Fail2ban:
```bash
sudo fail2ban-client status
sudo fail2ban-client status sshd
```
Убедись, что jail `sshd` активен.

## 9. Шаг 7 — автоматические security updates

```bash
sudo apt install -y unattended-upgrades
```
Проверка без применения:
```bash
sudo unattended-upgrade --dry-run --debug
```
Автоматический reboot сервера **не включай** — по умолчанию его не должно быть, перезагрузка должна происходить в контролируемое окно после проверки backup и состояния сервиса (это уже относится к моменту, когда сайт будет жить на сервере).

## 10. Шаг 8 — каталоги платформы

Создай с явными владельцами (не выполняй одной длинной командой — отдельными, чтобы видеть результат каждой):

```text
/opt/wisteria-platform/edge/
/opt/wisteria-platform/bin/
/opt/wisteria-apps/website/
/etc/wisteria/website/           # секреты сайта, root:root 0700/0600
/var/lib/wisteria/website/
/var/lib/wisteria-backup-staging/
/var/log/wisteria/
```

Секреты (каталог `/etc/wisteria/`) — права не шире `0600` на файлы, `0700` на каталоги, владелец `root:root`. Production-секреты никогда не размещаются в `/opt/wisteria-apps`, в git-чекауте или в домашнем каталоге пользователя `deploy`.

Каталоги для будущих сервисов (`/opt/wisteria-apps/inventory/`, `/opt/wisteria-apps/loyalty/`, аналогичные `/etc/wisteria/inventory/` и т.д.) создавать пока не нужно — их заводить в момент, когда эти сервисы действительно начнут разрабатываться, не заранее.

## 12. Где твоя зона ответственности заканчивается

После шага 10 сервер готов принять приложение, но само приложение разворачивать пока не нужно:

- в `website_visteria` ещё нет production Dockerfile / production Compose / CI-пайплайна (runbook §10) — это блокер, снимается другой работой над репозиторием сайта, не действиями на сервере;
- домен/DNS/TLS (runbook §12), генерация production-секретов (runbook §11), первый деплой (runbook §13), backup-стратегия (runbook §14), решение про email/Postfix (runbook §15), application security gate (runbook §16) и мониторинг (runbook §17) — следующие фазы, для них нужны отдельные решения пользователя (домен, платёжные/интеграционные секреты, готовый код приложения) и, вероятно, отдельное задание для агента, когда до этого дойдёт очередь.
- апгрейд конфигурации сервера (RAM/CPU/диск) делает пользователь сам в панели Beget — это не команда по SSH; ты можешь только подсказать, когда по текущим показателям (`free -h`/`df -hT`, раздел 4 этого задания) пора об этом напомнить пользователю, ориентируясь на пороги из `13_server-capacity-and-services-plan.md`.

Если пользователь попросит продолжить дальше этих границ — уточни явно, какая часть блокеров уже снята (домен выбран? секреты готовы? Dockerfile/Compose в репозитории появились?), прежде чем действовать.
